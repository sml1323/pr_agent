# ADR 0001 — 프로젝트 착수 결정

**날짜**: 2026-07-27
**상태**: 확정
**맥락**: `03-build-plan.md` §5의 미결 질문 6개를 착수 전에 확정.

---

## D1. 하네스는 직접 만든다 (Genesis Kit 안 씀)

**결정**: Genesis Kit을 쓰지 않고, 핵심 3개만 직접 굴린다.
1. `DONE.md`를 에이전트가 못 고치는 파일로 고정
2. 마일스톤마다 실제로 돌릴 수 있는 데모 명령 하나
3. 빌더가 아닌 **별도 세션**이 독립 검증

**근거**: 영상 화자 본인이 경고함 — **Genesis Kit은 설계를 먼저 한 사람에게만 도움이 되고, 설계 없이 쓰면 오히려 길을 잃게 한다** [03:08:21]. 그리고 이 3개를 손으로 굴려보면 왜 필요한지 몸으로 알게 되고, 그 뒤에 Genesis를 보면 훨씬 잘 읽힌다.

**포기하는 것**: Genesis Kit이 제공하는 인지 스킬 로스터 [02:27:51] — detective(디버깅) / verify(출력 검증) / blueprint(빌드 전 설계) / scout(옵션 탐색) / council·mirror(적대적 자기검토) / ghost(섀도·이월) / forecast(실패 예측).

**보완**: 위 목록을 **체크리스트로 쓴다.** 최소한 셋은 손으로라도 흉내낸다.
- **blueprint** — 코드 쓰기 전에 설계 먼저
- **verify** — 빌더 아닌 쪽이 확인 (= 결정의 3번)
- **forecast** — 만들기 전에 실패를 열거

나머지(scout·council·ghost)는 없어도 M8까지는 굴러간다.

**되돌리기**: 언제든 Genesis Kit으로 갈아탈 수 있다. 오히려 M2~M3쯤에서 직접 굴려본 뒤에 붙이면 훨씬 잘 읽힐 것.

---

## D2. 범위는 M8까지

**결정**: M0~M8만 구현. M9(신뢰성)~M12(피드백 루프)는 설계 문서로만 남긴다.

**근거**: M8이 **선별(자동 게시 vs 사람 큐)이 실제로 도는 지점**이고, 이 시스템의 존재 이유가 실현되는 곳이다 — "자신 있는 건 자동, 애매한 건 사람" [00:38:27]. 여기까지 도달하면 나머지는 "이미 아는 실패에 방어 붙이기"라 성격이 다르다.

영상 화자도 카메라 앞에서는 웹훅 인그레스와 데이터 레이어까지만 만들고 나머지는 시청자에게 넘겼다 [03:06:33].

**되돌리기**: M8 완주 후 다시 결정. 범위를 늘리려면 `DONE.md`를 사람이 직접 고친다.

## D3. DB는 처음부터 Tiger Cloud

**결정**: 로컬 Docker를 건너뛰고 처음부터 TigerData Tiger Cloud. `docker-compose.yml`은 만들지 않는다.

**근거**: 빌드 플랜의 추천은 (c) "M0~M6 로컬 → M7부터 Tiger"였으나 채택하지 않았다. 채택하지 않은 이유가 곧 이 결정의 근거다 — **Tiger MCP를 붙이면 코딩 에이전트가 프로비저닝·마이그레이션·검증 SQL을 직접 실행한다** [02:51:04]. 사람이 콘솔을 클릭하는 대신 인프라 셋업도 코드와 같은 감사 루프 안으로 들어온다. 그 경험 자체가 이 프로젝트의 학습 목표에 속한다.

부차적으로, 영상이 Tiger를 고른 논거에 **엔터프라이즈 실사용 신뢰성**이 있다 [01:16:28][01:25:17] — 인기 때문이 아니라.

**받아들이는 비용**: 초반 마이그레이션을 수십 번 갈아엎는데 로컬보다 느리다. 네트워크·인증 문제가 학습을 방해할 수 있다. M2에서 체감될 것.

**완화**: 마이그레이션은 반드시 **재실행 가능(idempotent)하게** 쓴다. `DROP ... IF EXISTS` → `CREATE`. 갈아엎기가 잦을 걸 알고 시작하므로 처음부터 그렇게 쓴다.

**주의**: 결제 실패로 서비스가 **조용히 pause**될 수 있다 — 영상 화자 본인의 서비스가 그래서 죽어 있었다 [02:48:27]. 크레딧 만료일을 캘린더에 적어둘 것.

## D4~D6. 추천안 그대로 채택

| | 결정 | 근거 |
|---|---|---|
| **리뷰 대상 레포** | 개인 토이 레포에 일부러 버그를 심어서 | **정답을 내가 안다**는 것 하나 때문. 에이전트가 진짜 잡았는지 운이었는지 즉시 판별됨. 레포는 작을수록 좋음(임베딩 비용·인덱싱 시간) |
| **학습 비중** | 설계 사고 60% / 완성 30% / 하네스 10% | 영상 화자가 "가져갈 자산은 이 에이전트가 아니라 **설계 루프**"라고 명시 [00:05:13] |
| **LLM 제공자** | OpenAI 하나 (LLM + 임베딩) | 초반 변수 축소. 임베딩 차원·구조화 출력·비용 계산이 한 곳에서 일관됨 |

**LLM 관련 후속**: 원래 계획은 M11(평가)에서 제공자를 바꿔보며 회귀 게이트가 차이를 잡아내는지 확인하는 것이었다. **D2로 M11이 범위 밖이 됐으므로 이 실습은 하지 않는다.** 모델 라우팅(에이전트별로 다른 모델 [01:48:58])은 M6에서 설정 파일 수준으로만 만들어두고, 실제 교체 실험은 하지 않는다.

## 결정하지 않은 것

- **코드 청킹 전략** — 영상에서 불명확. M7 착수 시 별도 ADR로. 테스트 레포가 단일 언어면 tree-sitter, 여러 언어면 라인 윈도우 + 오버랩으로 시작.
- **HTTP 200 vs 202** — 영상은 200을 두 번 명시 [01:28:30][01:31:39]. 200으로 간다. 202가 의미상 더 정확하지만 영상과 어긋나게 할 이유가 없다.
- **임베딩 차원** — `text-embedding-3-large`의 기본은 3072. 영상엔 `vector(1536)` 스키마와 `.env` 256이 충돌하는 사례가 나온다 [03:03:59]. **M2에서 한 곳(마이그레이션)에만 정의하고 코드가 거기서 읽게 한다.** 값 자체는 M2 착수 시 결정.

## 1. 문제 정의 — 왜 "LLM + RAG"로는 안 되나

### 1.1 나이브 베이스라인부터 정확히 짚기

영상은 대부분의 튜토리얼이 만드는 것을 이렇게 정의함 `[00:00:00]`:

```
PR diff → completion 프롬프트("이 코드 뭐가 잘못됐어?") → (옵션) RAG로 관련 파일 몇 개 첨부 → 끝
```

발표자 주장: 이런 모양의 튜토리얼이 대략 400개 있고, **하나도 프로덕션급 에이전트 시스템이 아님**. 중요한 건 이게 *기술적으로* 틀렸다는 게 아니라 **문제를 잡는 층위(problem framing)에서 틀렸다**는 것 `[00:00:00]`.

### 1.2 기존 자동화 4종의 실패 이유 (각각 다르게 실패함) `[00:51:24]`

| 접근 | 하는 일 | 왜 부족한가 |
|---|---|---|
| 린터(linter) | 패턴 · 문법 · 스타일 규칙 매칭 | 의도(intent) · 로직 · 의미론을 **추론 못 함** |
| 정적 분석(static analysis) | 데이터 흐름 · 타입 분석 | 진짜 버그는 잡지만 오탐(false positive)이 많고, 코드베이스 전체 맥락 판단이 없고, 문서를 못 읽음 |
| 단일 LLM diff 리뷰 | 프롬프트 하나로 diff 전체 훑기 | ① 서로 다른 4개 관심사에 **마인드셋 1개**만 적용 ② 레포에 대한 그라운딩(grounding, 근거 붙잡기) 없음 ③ 컨텍스트가 커질수록 자신 있게 환각 ④ 감사(audit)·관측 불가 |
| 전체 레포를 프롬프트에 붙이기 | "그냥 다 넣지 뭐" | 컨텍스트 윈도우 고갈 → 출력 품질 급락 `[00:54:31]` |

한 줄 요약: **에이전트 하나에 일을 너무 많이 주면 성능이 떨어짐** `[00:51:56]`. 이게 나중에 4개 전문 에이전트로 쪼개는 직접적 근거가 됨.

### 1.3 그리고 절반은 아예 빠져 있음 — 엔지니어링 실패 `[00:03:06]`

"LLM + RAG" 프레이밍은 **모델 실패**만 본다. 실제 프로덕션에선 인프라·프로토콜 실패가 따로 있고, 이건 프롬프트를 아무리 잘 써도 안 사라짐.

- GitHub가 **같은 웹훅을 재전송** → 같은 PR을 두 번 리뷰하고 두 번 과금 (멱등성 필요)
- GitHub인 척하는 **위조 요청** → 서명 검증 필요
- **타이밍 불일치**: ack 창은 짧고 에이전트는 느림. 단, 소스가 수치를 **두 세트**로 말함 (자세한 건 §6.2)
  - `[00:03:06]` — GitHub은 **~10초** 안에 ack 기대 vs 에이전트는 **~90초** 소요
  - `[01:31:39]` — ack 창 **~10~12초** (화자가 "정확한 수치는 확실치 않다"고 직접 말함) vs 전체 LLM 리뷰 **30~40초+**
  → 어느 수치를 쓰든 결론은 같음: 웹훅 핸들러 안에서 LLM을 부르면 무조건 타임아웃

### 1.4 진짜 문제 재정의 — 두 번의 리프레임

**리프레임 1 — 시스템을 지우고 사람을 봐라** `[00:34:18]`
자동 리뷰어가 없으면 뭐가 아픈가:
- PR이 시니어의 시간을 기다리며 **몇 시간~며칠** 쌓임 (발표자는 ZenML 등에서 제대로 된 코멘트 받는 데 일주일 걸린 적도 있다고)
- **비일관성**: 리뷰어마다, 날마다 지적하는 게 다름
- **피로**: 그날의 10번째 리뷰는 1번째 리뷰와 같은 품질이 아님

세 가지 통증이 전부 한 가지를 가리킴 — **희소 자원은 리뷰 처리량이 아니라 시니어의 주의력(attention)**.

**리프레임 2 — 문제 문장을 바꾼다** `[00:36:22]`

> ❌ "PR을 자동으로 리뷰하는 에이전트를 만든다"
> ✅ "리뷰의 **기계적인 부분**을 자동화해서 **시니어의 주의력을 되찾아주는** 에이전트를 만든다. 인간의 판단은 정말 필요한 곳에만 쓰이게."

### 1.5 L0 제1원칙 — selectivity(선별성) `[00:38:27]` `[00:38:58]`

> **시스템은 "시니어가 볼 가치가 있는 발견을 드러내고 나머지는 미루는 것"을 최적화한다. 출력량 최대화가 아니라.**

왜 이게 전부인가: 모든 줄에 코멘트 다는 에이전트는 **아끼려던 그 주의력을 오히려 태워버림**. selectivity 한 문장에서 뒤의 모든 결정이 따라 나옴 — HITL 게이트를 어디 둘지, 관측성을 왜 만들지, 보안 경계를 어디에 그을지, 실패를 어떻게 처리할지 `[00:38:58]`.

> ⚠️ 리뷰 에이전트는 인간 판단의 **대체제가 아님**. 인간 판단을 *희소하게, 잘 조준되게* 만드는 도구.

## 2. 시니어 엔지니어는 PR을 어떻게 리뷰하나

설계 방법론 자체가 이거임 `[00:01:32]` `[00:06:47]`:
1. AI를 그림에서 **지운다** → 오늘 이 일을 하는 사람을 관찰
2. **무의식적인 micro-step까지** 전부 받아 적는다 (여기엔 지름길 없음, 순수 수작업)
3. 각 단계를 "기계적 / 인간 판단"으로 분류 → LLM 자리, 결정론적 ML 자리, 사람 자리가 갈림
4. 인간 프로세스가 **어디서 깨지는지**도 기록

### 2.1 관찰된 4가지 행동 `[00:41:04]`

1. **코드베이스 컨텍스트를 들고 옴** — 과거 결정, 아키텍처 스타일, 기존 컨벤션에 대조
2. **분리된 관심사를 따로따로 추론** — 보안 / 정확성 / 테스트 / 문서 / 가독성, 각각 별개 마인드셋
3. **회의적** — diff가 맞다고 전제하지 않음
4. **증거를 인용** — "이거 좀 이상한데"가 아니라 **"40번 줄에서 null이 될 수 있음"**. 모호한 지적은 아무도 조치할 수 없으니까

### 2.2 오늘의 실제 PR 흐름 → 컴포넌트 매핑 `[00:08:53]` `[00:46:14]`

| # | 사람이 하는 일 | 관찰 내용 / 왜 중요한가 | 매핑되는 컴포넌트 |
|---|---|---|---|
| 1 | 개발자가 커밋 push → PR 오픈 | 여기가 정확한 시작점 | — |
| 2 | 리뷰어가 알림으로 인지 (GitHub 알림 / Slack / Discord / "나 PR 올렸는데 봐줄래?") | 트리거는 **정밀**해야 함. "아무 이벤트나"는 설계 버그 | **Events** — GitHub `pull_request` 웹훅 (PR opened/updated) `[00:47:16]` |
| 3 | PR이 대기 상태로 방치 | 순수 낭비 비용 ①: **대기 시간** | 큐(Redis + ARQ) + 워커 — ack와 작업을 분리 |
| 4 | 리뷰어가 컨텍스트 스위칭 | 순수 낭비 비용 ②: **컨텍스트 스위칭** | 오케스트레이터가 대신 컨텍스트를 조립 |
| 5 | diff를 읽음 | 추가(+/초록) · 삭제(−/빨강) 줄 | PR diff fetch (GitHub API) |
| 6 | 머릿속 코드베이스 지식을 꺼냄 (ADR, 문서, 관련 모듈) | **에이전트는 이게 없음 = 그라운딩 문제** | **Retriever** — RAG. 유사 코드 + *영향받을* 코드 둘 다 `[00:13:34]` |
| 7 | 마인드셋을 바꿔가며 4개 관심사 검토 | 하나의 추론기로는 못 함 | **4개 전문 에이전트 병렬 fan-out** `[00:45:43]` |
| 8 | 때로 브랜치를 pull 해서 직접 실행 | 관찰된 행동. 이 빌드에서 구현했는지 여부는 *(소스에 근거 없음 — 추정)* | — |
| 9 | 근거를 달아 코멘트 | 파일·라인 앵커 + 이유 | **Finding 스키마** (rationale + confidence + file/line) `[00:47:47]` |
| 10 | 확신 없으면 더 시니어에게 에스컬레이션 | 사람도 자기 confidence로 라우팅함 | **HITL 게이트 + 승인 큐** `[01:03:27]` |
| 11 | 공개 PR의 심각한 보안 취약점은 **공개 스레드에 안 씀** | 공개하면 패치 전에 악용됨 | 보안 발견은 private 채널(Slack/DM)로 out-of-band `[00:11:59]` |
| 12 | 개발자가 코멘트를 읽고 반박 or 수정 후 재제출 | 되돌릴 수 있음 = 가역성 | dispute 기록 → 학습 루프 `[01:06:03]` |

**핵심**: 에이전트 개수 4개는 "멀티 에이전트가 멋있어서"가 아니라 **사람이 실제로 4개 마인드셋을 쓰기 때문에** 나온 숫자 `[00:02:35]`.

## 4. 리트리벌 & 컨텍스트 엔지니어링

### 4.1 왜 리트리벌인가 — 결론이 아니라 도출 `[00:54:31]`

시니어 리뷰어에겐 **그라운딩 문제가 없음**. 레포를 이미 알고 있으니까. diff만 던져받은 에이전트는 **낯선 사람(stranger)**.

- 전체 레포를 프롬프트에? → 원리적으론 가능, 실전에선 불가 (컨텍스트 윈도우 고갈 + 출력 품질 붕괴)
- 그래서 답은 **diff마다 가장 관련 있는 코드 조각만 가져오기** = **컨텍스트 엔지니어링**
- 발표자 표현: **"리트리벌이 낯선 사람을 동료로 만든다"**

> 순서에 주목. "RAG를 쓰자"에서 시작한 게 아니라 **문제에서 RAG가 도출됨**.

**리트리벌 목표는 하나가 아니라 둘** `[00:43:38]`:

| 무엇을 당겨오나 | 왜 |
|---|---|
| diff와 **비슷한** 코드 | 컨벤션·패턴 대조. "우리는 원래 이렇게 짜는데?" |
| diff가 **영향을 줄 수 있는** 코드 | blast radius. "이게 다른 데를 뭘 깨뜨리나?" |

발표자는 이 둘째 축을 **contextual RAG**라고 부르고 뒤에서 따로 다루겠다고 명시함 `[00:43:38]`. 이 구분이 리트리벌 설계의 핵심 — 닮은 코드만 가져오면 리뷰어가 하는 일의 **절반만** 한 것.

### 4.2 메모리 3종 → 데이터 shape 3종 `[00:56:37]` `[00:59:15]` `[01:11:18]`

사람 엔지니어가 들고 있는 기억을 그대로 옮김:

| 메모리 종류 | 사람 기준 | 시스템 기준 | 필요한 쿼리 패턴 | 저장 형태 |
|---|---|---|---|---|
| **Semantic** (의미 기억) | 코드베이스 자체 — 함수, 클래스, 현재 컨벤션, ADR(architecture decision record, 아키텍처 결정 기록) | `code_chunks` 임베딩 | 유사도(nearest neighbor) 검색 | pgvector 벡터 컬럼 |
| **Episodic** (일화 기억) | 과거 리뷰 — 뭘 지적했고 뭐가 반박당했나 | review / findings 행 | **시간순** 조회 (2021년 결정을 2022년 결정이 덮어씀) | 타임스탬프 붙은 관계형 행 |
| **Procedural** (절차 기억) | "우리 팀은 이렇게 함" = 컨벤션 | 규칙 셋 | 작고 구조화된 조회 | 일반 관계형 행 |

여기에 하나 더, 나중에 도출되는 **4번째 shape**:

| **Time** (관측성) | 무슨 일이 언제 얼마 비용으로 일어났나 | `agent_events` | 최근 구간 스캔 + 롤업 | TimescaleDB hypertable + continuous aggregate |

그리고 데이터를 3개 **shape**로 다시 묶음 `[01:11:18]`:
- **MEMORY** — 에이전트가 *읽는* 것 (코드 청크 + 과거 리뷰 + 컨벤션)
- **TRUTH** — 에이전트가 *만들어낸* 것 (findings, GitHub review ID, 에스컬레이션 여부, 사람의 결정)
- **TIME** — *무슨 일이 있었는지* (span, LLM 호출, 툴 호출, 비용, 지연, 결정)

### 4.3 "DB 3개" 문제 — 그리고 왜 결국 1개로 갔나 `[01:09:12]` `[01:14:25]`

⚠️ 오해 방지: 영상의 결론은 **"DB 3개를 쓴다"가 아니라 "shape 3개를 유지하되 DB는 1개로 합친다"**임.

나이브한 본능:

| shape | 나이브 선택 |
|---|---|
| MEMORY | 전용 벡터 DB (Qdrant 같은) |
| TRUTH | Postgres |
| TIME | 별도 시계열 스토어 |
| (+ 컨벤션) | 또 다른 뭔가 |

발표자가 이걸 깨는 **단일 스모크 테스트 질문** `[01:14:56]`:

> "이 PR에 대해 — 우리가 어떤 코드를 가져왔고, 어떤 리뷰를 내놨고, 어떤 모델 호출이 비쌌나?"

DB가 3개면 이 평범한 질문 하나에 **쿼리 3번 + 파이썬에서 수동 결합**. 그리고 진짜 비용은 요금이 아니라 운영:
- 커넥션 풀 3세트 · 백업 절차 3세트 · 보안 모델 3세트
- **독립적인 실패 모드 3세트** — 하나 죽으면 파이프라인 전체가 죽음

> 원칙: **shape는 모델링 개념이지 프로비저닝 개념이 아님** `[01:09:12]`.
> "기능마다 DB 하나" 는 명시적 안티패턴.

**선택: Tiger Cloud (TigerData의 매니지드 Postgres 호환 DB)** `[01:16:28]`
- 선택 기준은 "인기 있어서"가 **아니라** "**세 shape를 동시에 담을 수 있어서**"
- 얻는 것: 내구 DB 1개, 백업 스토리 1개, 쿼리하는 곳 1개, memory·truth·time을 잇는 **동일 ID 1개**
- **Redis는 남김** — 잡 큐는 "내구 저장 shape"가 아니라 작업 스크래치패드라서 통합 대상이 아님 `[01:24:14]`
- 보조 논거: **엔터프라이즈가 실제로 굴리고 있다**는 실사용 신뢰성(+ 이력서에도 쓸 수 있는) 근거를 같이 듦 `[01:16:28]` `[01:25:17]`. 단 이건 뒷받침용이지 1차 선택 기준이 아님 — 1차 기준은 어디까지나 "세 shape를 동시에 담는가"
- 참고: 리뷰 행 + finding 행만 필요했다면 **순수 Postgres로 충분**했음. 벡터 검색과 시계열 쿼리가 확장(pgvector·TimescaleDB)을 강제한 것 `[01:25:17]`

전용 벡터 DB(Qdrant) 대비 논거 `[01:26:21]`:
> PR 리뷰 쿼리 = 벡터 유사도 **+** 레포 필터 **+** 최신성 **+** 정확한 식별자 매칭 **+** 리뷰 기록 **+** 비용 기록 **+** 감사 이력.
> 순수 ANN 성능이 조금 더 좋은 것보다, **리트리벌이 메타데이터·감사 트레일 바로 옆에 있는 것**이 더 값짐.

## 7. 오케스트레이션 설계

### 7.1 왜 LangGraph인가 — ADR로 기록된 비교 `[01:38:27]`

| 차원 | LangGraph | Temporal |
|---|---|---|
| 인프라 | 기존 Python 프로세스 안에서 실행, **추가 인프라 0** | 별도 서버 운영 필요 |
| 병렬 fan-out | **Send API로 일급 지원** | 지원은 되지만 표현이 무거움 |
| 체크포인트 | 이미 큐로 쓰는 **Redis에 그대로** 저장 | 내구성 보장이 더 강하고 실패 복구도 우수 |
| LLM 통합 | LLM 워크플로 전용, 툴링 좋음 | 범용 워크플로 엔진 (LLM 특화 아님) |
| 성숙도 | 신생, 상대적으로 미검증 | 엔터프라이즈급, 대규모에서 탁월 |
| 운영 비용 | 앱 외 추가 비용 없음 | 서버 운영 + 워크플로 모델 학습 부담 |

**결론은 조건부**: "MVP에는 LangGraph. Temporal은 나쁜 후보가 아니고 나중에 맞는 선택일 수 있음."

> 그래서 **되돌릴 수 있게** 만듦 `[01:40:33]`:
> ```
> abstract class WorkflowEngine:
>     run(...)        # 워크플로 실행
>     resume(...)     # 중단 지점부터 재개
>     get_state(...)  # 현재 상태 조회
> ```
> Temporal로 갈아타는 건 **구현 클래스 하나 추가**이지 재작성이 아님.
> 원칙: **시스템 전체를 프레임워크 하나에 용접하지 말 것. "이거 갈아타기 얼마나 어렵나"가 설계 기준 그 자체** `[00:30:42]`.

### 7.2 그래프 구조

- **노드** = 함수 또는 LLM 호출
- **엣지** = 다음에 뭐가 실행될지 결정
- **fan-out**: 4개 전문가 병렬 (Send API)
- **fan-in**: aggregator 노드 하나로 수렴

**왜 병렬이 허용되나** `[01:36:19]` `[01:59:50]`:
> 4개 전문가는 **서로의 출력을 소비하지 않음**. 그래서 직렬화하면 지연만 늘어남.
> 반대로 발표자는 동적/병렬 에이전트 워크플로를 **기본값으로는 반대**함 — 실제 프로젝트 태스크는 대개 상호 의존적이라 병렬화가 속도가 아니라 충돌을 만듦.
> **"협업이 필요 없다는 게 증명될 때만 병렬화"** — 이 조건을 만족하니까 여기선 병렬이 정답.

### 7.6 인그레스(ingress) 상세 — 트러스트 바운더리 `[01:28:30]` `[02:43:58]`

아마존 택배 비유: **맞는 주문인지 확인 → 서명 → 문 닫음 → 그다음에 내용물 처리** `[01:28:30]`.

⚠️ **순서에 대해 소스가 두 군데서 다르게 말함** — 어느 쪽도 확정 사실로 단정하지 말 것:

| 어디서 | 말한 순서 |
|---|---|
| 설계 진술 `[01:30:05]` | ① **raw payload에 대한 HMAC 서명 검증** → ② `pull_request` 이벤트로 필터 → ③ 멱등성 키 |
| 내레이션 `[01:28:30]` | **PR로 먼저 좁힌 뒤**, 어떤 작업이든 하기 전에 서명 검증 |

> 💡 실무 권고: **HMAC은 raw body 바이트에 대해 계산**되므로, body를 파싱하거나 이벤트 타입으로 거르기 **전에** 검증하는 쪽이 안전함. 파싱·재직렬화가 서명 대상 바이트를 바꿔버릴 수 있고, 서명 검증 전에 body를 건드리는 것 자체가 미인증 입력을 처리하는 일이라서.

아래는 그 권고를 따른 순서 (하나라도 실패하면 즉시 리턴):
1. **HMAC 서명 검증 (raw body)** — 여기가 보안 경계. 출처를 증명 못 하면 **아무 일도 하지 않음**
2. 이벤트 타입이 `pull_request`인가 — GitHub는 star, push 등 **모든 레포 이벤트**를 보냄
3. JSON 파싱
4. 내부 포맷으로 정규화
5. 멱등키(delivery ID)로 중복 확인 — 재전송이면 ack하고 drop
6. Redis(ARQ)에 enqueue → GitHub에 즉시 200

> 서명 + 멱등키를 발표자는 **"OTP 확인하듯 독립된 두 겹의 방어"**로 비유 `[01:30:05]`.

HTTP 상태 코드 규칙 (실제 퀴즈로 다뤄진 부분) `[02:39:42]` `[02:41:18]`:
- **서명 검증 실패 → 이유 불문 고정 `400`**. 응답을 획일화해서 공격자에게 아무 신호도 안 줌
- **서명은 유효한데 본문이 깨진 경우 → `500` 아니라 `400`**.
  근거: HMAC이 통과했다는 건 발신자가 **공유 비밀을 갖고 있다는 증명** = 인증된 호출자. 인증된 호출자가 보낸 잘못된 본문은 **클라이언트 오류**.
  실무 이득: 서버 모니터링 오탐 없음, 웹훅 연동 디버깅 쉬움, HTTP 의미론에 맞음.

트러스트 바운더리 2개를 명시적으로 선언 `[02:06:53]`:
1. 웹훅 HMAC 서명 일치
2. **PR diff는 신뢰할 수 없는 입력** — PR을 열 수 있는 누구나 넣을 수 있으므로 **프롬프트 인젝션 벡터**로 취급

### 8.2 검증(verification-first)

**핵심 논증 — 자기 시험지 채점 금지** `[01:56:44]`:
> 모델이 자기 테스트를 쓰게 하면 **자기가 시험 문제 내고 자기가 채점**하는 것. 자기가 통과할 수 있는 문제만 낸다.
> 선생님이 유효한 시험을 낼 수 있는 이유는, **당신 머릿속 추론을 몰라도 입력/출력 계약(contract)은 알기 때문**.
> → 테스트는 **구현하는 에이전트 바깥**에서 와야 함.

검증 장치들:

| 장치 | 내용 |
|---|---|
| **마일스톤당 데모 커맨드 딱 1개** `[02:07:57]` | 코딩 에이전트는 **실행조차 안 되는 코드를 성공이라고 선언**함. 실행 가능한 데모가 "완료"를 에이전트의 의견에서 **관찰 가능한 사실**로 바꿈 |
| **L4 독립 검증자** `[02:37:06]` | 완전히 새 컨텍스트의 에이전트를 띄우고 **목표 + 성공 기준 + 불변식만** 줌. **빌더의 추론 흔적은 절대 안 줌** — 빌더의 컨텍스트를 읽은 검사자는 빌더의 맹점을 그대로 물려받으니까. 프롬프트에 "너는 독립 코드 리뷰어다, 코드를 쓰지 마라, 빌더의 주장을 참이라고 가정하지 마라" 명시 |
| **quiz-me (사람 이해도 게이트)** `[02:35:33]` `[03:00:45]` | 빌드 후 **사람에게** 퀴즈. 3가지 유형: 설계 근거 / 엣지 케이스 / 변경 영향. "괜찮아 보이네"로 도장 찍지 말 것 |
| **kickoff interview** `[02:35:33]` | 마일스톤을 쓰기 **전에** 사람을 인터뷰 → 올바른 것이 만들어지게 |
| **골든 데이터셋 + 회귀 게이트** `[01:49:29]` | 새 프롬프트나 모델은 **현재 배포된 시스템을 이겨야만** 나감. 아니면 차단 |
| **프롬프트 레지스트리** `[01:49:29]` | v1, v2… 덮어쓰지 않고 버전 보관 → 나쁜 리뷰를 **정확히 어느 프롬프트가 만들었는지** 역추적 |
| **DB 레벨 불변식 강제** `[02:55:58]` | `agent_events`는 append-only. UPDATE/DELETE를 **트리거로 DB가 직접 거부**. 관례는 잊히지만 DB 거부는 **물리적으로 불가능**하게 만듦. 테스트 데이터도 예외 없음 — **예외 하나는 모두에게 예외** `[02:57:26]` |

**검증이 실제로 잡은 버그 3개** (전부 빌더는 "성공"이라고 보고했던 것):

| 버그 | 잡은 곳 |
|---|---|
| 서명은 유효한데 본문이 깨진 페이로드 → 그냥 `500` 크래시 | L4 검증자 `[02:38:39]` |
| `TRUNCATE`는 row-level DELETE 트리거를 **발동시키지 않음** — append-only 테이블이 통째로 비워질 수 있음. 별도의 `BEFORE/AFTER TRUNCATE` 트리거 필요 | L4 검증자 `[03:02:54]` |
| 임베딩 차원 불일치 `vector(1536)` vs `EMBEDDING_DIMENSION=256` | quiz-me의 "변경 영향" 질문 — **임베더 코드가 존재하기도 전에** `[03:03:59]` |

관련해서 실제로 부딪힌 엔진 제약: **Postgres RULE은 TimescaleDB hypertable에서 못 씀** `[02:53:47]` `[03:00:45]`. RULE은 쿼리 재작성(query-rewrite) 단계에서 동작하는데, hypertable은 데이터를 여러 chunk 테이블에 흩어놓고 재작성 룰을 지원하지 않음 → `CREATE RULE` 자체가 에러. 그래서 **트리거** 방식으로 전환. 그리고 이런 제약은 **실제 엔진에 직접 마이그레이션을 돌려야만** 드러남 (로컬 대체 Postgres였으면 한참 뒤에 터졌을 것) `[02:53:47]`.

### 8.3 Genesis 리추얼 — 하네스 기반 AI 개발

**뭔가**: 발표자가 만든 오픈소스 **하네스(harness)**. 코딩 에이전트에게 지속되는 상태(state)와 올바른 컨텍스트를 주는 층 `[00:04:09]` `[01:56:13]`.

**왜 쓰나** (해결하는 문제):
- 새 세션을 열면 에이전트가 **이미 쓴 코드를 또 씀**, 컨텍스트 윈도우가 터짐, 환각, 목표 드리프트 `[01:56:13]`
- 코딩 에이전트는 마찰을 만나면 **목표를 자기 편한 대로 조용히 다시 정의**함 `[02:02:24]`
- 코딩 에이전트는 **실행도 안 해본 코드를 완료라고 선언**함 `[02:07:57]`

**구성 요소**:

| 산출물 | 역할 |
|---|---|

**빌드 순서** (의존성 우선, 인프라 먼저) `[02:13:08]` `[02:59:30]`:

```
인지 설계 → 시스템 아키텍처(모듈러 모놀리스) + ADR → 프론트엔드 대시보드 →
백엔드 API → 오케스트레이션 → LLM & 추론 → 메모리 → 툴링 →
평가 → 관측성 → 보안 → 신뢰성 → 거버넌스 / DX / CI-CD / HITL / 지속 학습
```

이름만 봐선 안 보이는 페이즈들의 실제 내용 `[01:47:56]`:

| 페이즈 | 내용 |
|---|---|
| LLM & 추론 | 에이전트별 모델 라우팅 + 프롬프트 레지스트리 |
| 평가 | 새 프롬프트/모델은 골든 데이터셋에서 **현재 배포본을 이겨야** 통과. 아니면 회귀 게이트가 차단 |

| **보안** | **RBAC 강제** + **불변 감사 추적(immutable audit trail)** |

발표자는 이 중 일부만 카메라 앞에서 짓고 나머지는 시청자 몫으로 남긴다고 밝힘.

## 10. 핵심 교훈

1. **기술이 아니라 사람에서 시작한다.**
   AI를 그림에서 지우고, 오늘 그 일을 하는 사람을 관찰하고, 무의식적 micro-step까지 받아 적어라. 어려워 보이는 문제는 대개 **사람이 이미 푼 문제**다. 아키텍처 다이어그램에서 시작하면 없는 문제를 발명하고 있는 문제를 놓친다. `[00:06:47]` `[00:41:34]`

2. **문제 문장을 다시 써라. 대부분의 시스템 설계는 리프레임이 필요하다.**
   "PR을 자동 리뷰한다" → "시니어의 주의력을 되찾는다". 이 한 문장의 차이에서 **selectivity(선별성)**가 나오고, selectivity에서 HITL 위치·관측성·보안 경계·실패 처리가 전부 따라 나온다. **커버리지가 아니라 선별성**. `[00:36:22]` `[00:38:58]`

3. **실패를 두 방향에서 세라 — 엔지니어링과 LLM.**
   한쪽만 열거하면 시스템의 절반이 무방비다. 그리고 실패를 다 분류하고 나면 설계가 스스로 쓰이기 시작한다. 코드는 다섯 컴포넌트(orchestrator / retriever / events / gate / state)에 같은 루프를 다 돌린 **다음**에 짜라. `[00:03:06]` `[00:03:37]`

4. **자율성은 기본값이 아니라 논증의 결과다.**
   결과의 심각도 · 가역성 · 시스템 성숙도 세 축으로 정하고, **평균이 아니라 최악**으로 설계하라. 100개 중 99개 맞아도 그 하나가 치명적이면 실패한 시스템이다. 사람을 많이 넣고 시작해서 줄여가는 게, 자동화로 시작해서 사고 후에 감독을 붙이는 것보다 훨씬 싸다. `[00:15:37]` `[00:26:03]` `[00:27:05]`

5. **모든 주장에 증거를 달아라 — rationale + confidence + file/line.**
   "이거 좀 이상한데"는 아무도 조치 못 한다. "40번 줄이 null 될 수 있음"은 조치 가능하다. 그리고 **confidence 자체가 틀릴 수 있으므로** rationale이 필요하다 — 어느 추론 단계가 깨졌는지 되짚는 유일한 실마리. 신뢰의 세 기둥은 **추론 · 그라운딩 · 증명(proof)**. `[00:44:41]` `[01:00:17]`

6. **shape는 모델링 개념이지 프로비저닝 개념이 아니다.**
   메모리 3종을 유지하되 DB 3개를 만들지 마라. 평범한 질문 하나("이 PR에 뭘 검색했고 뭘 내놨고 뭐가 비쌌나")에 쿼리 3번 + 파이썬 결합이 필요하면 레이아웃이 틀린 거다. 진짜 비용은 요금이 아니라 **독립적인 실패 모드 N세트**. `[01:09:12]` `[01:14:25]`

7. **프레임워크에 시스템을 용접하지 마라 — ADR은 되돌릴 수 있어야 한다.**
   `WorkflowEngine(run/resume/get_state)` 하나가 LangGraph→Temporal 전환을 "구현 클래스 추가"로 만든다. "이거 갈아타기 얼마나 어렵나"가 설계 기준 그 자체다. 그리고 **후보를 나열하지 못하면 고른 게 아니다**. `[01:40:33]` `[02:25:14]`

8. **자기가 낸 시험지를 자기가 채점하게 두지 마라 — 사람에게도 똑같이 적용된다.**
   테스트는 구현자 바깥의 입출력 계약에서 나와야 하고, 검증자는 빌더의 추론 흔적을 **못 봐야** 독립적이고, 성공 정의(DONE.html)는 에이전트의 쓰기 권한 밖에 있어야 하고, 불변식은 관례가 아니라 **DB가 물리적으로 거부**해야 한다. 그리고 사람도 "괜찮아 보이네"로 도장 찍지 말고 quiz-me로 스스로를 검증해라. 이 영상에서 실제로 잡힌 버그 3개는 **전부 빌더가 "성공"이라고 보고한 것들**이었다. `[01:56:44]` `[02:37:06]` `[02:55:58]`

Lesson 06 · M5 · backend/orchestration/

"아무 문제 없음"과
"아무도 안 봄"

병렬로 갈라놓는 순간, 빈 결과는 두 가지 뜻을 갖는다. 둘을 못 가르면 시스템이 조용히 거짓말한다.

여기서 땅이 또 바뀐다 01~05는 전부 혼자 도는 코드였다. 하나가 터지면 그 자리에서 터졌고, 터진 걸 바로 알았다.

M5부터는 넷이 동시에 돈다. 그러면 새로운 실패 방식이 생긴다 — 터졌는데 아무도 모르는 것. 이 레슨은 그거 하나만 다룬다.

장면부터

건강검진을 받았다. 피검사·엑스레이·심전도·초음파를 동시에 돌린다. 각각 다른 기사가 본다. 30분 뒤 결과지가 나온다.

이상 소견 없음.

그런데 엑스레이 기계가 고장나 있었다. 촬영이 아예 안 됐다. 결과지에 엑스레이 항목이 그냥 없다. 소견이 비어 있으니 "이상 없음"에 합산됐다.

우리 파이프라인의 ④→⑤가 정확히 이 모양이다. 

       ┌─ security ─┐   findings: []      ← 죽어서 빈 것
       │             │
PR ────┼─ quality ──┼──→ 애그리게이터 ──→ 게이트 ──→ 자동 게시
       │             │      "critical 없네"
       ├─ testing ──┤
       └─ docs ─────┘

용어 — 뒤 절 전체에서 계속 나온다 애그리게이터(aggregator)는 모으는 담당이다. 넷이 각자 낸 지적을 한 뭉치로 정리한다 — 이어붙이고, 중복을 빼고, 대표 숫자 하나(전체 확신도)를 뽑는다.

게이트와 하는 일의 종류가 다르다. 애그리게이터는 아무것도 결정하지 않는다 — 자르거나 버리지 않고 모양만 다듬어 넘긴다. 통과·차단은 전부 게이트 몫이다.

하는 일예
애그리게이터 ⑤정리"지적 5개 → 중복 빼고 3개. overall 0.95"
게이트 ⑥판단"0.95지만 critical이니 사람에게"

의사 넷이 각자 소견서를 썼고 간호사가 한 장으로 정리해 담당의에게 올리는 그림이다. 간호사는 진단을 안 내린다.

그래서 위 장면에서 게이트는 critical이 하나도 없는 걸 보고 자동 게시한다. 진실은 "보안 관점은 아무도 안 봤다"였다. 이 프로젝트의 제1원칙이 선별인데, 여기서 나오는 건 선별이 아니라 근거 없는 통과다.

빈 리스트는 "깨끗하다"와 "아무도 안 봤다"를
같은 값으로 만든다.

1. 그전에 — 병렬로 갈라도 되는 조건

넷을 동시에 돌리는 게 항상 옳은 건 아니다. 조건이 있다: 노드끼리 서로의 출력을 안 쓸 때만 병렬이 안전하다 [01:59:50].

우리 넷은 이 조건을 만족한다. security가 찾은 SQL 인젝션이 docs의 판단을 바꾸지 않는다. 각자 같은 diff를 읽고 각자 답한다.

이걸 안 따지고 병렬화하면 얻는 게 속도가 아니라 충돌이다.
B가 A의 결과를 필요로 하는데 동시에 돌리면, B는 A가 아직 안 쓴 값을 읽는다. 그러면 매번 다른 결과가 나오고, 재현이 안 되니 디버깅도 안 된다.

2. 갈라놓기는 한 줄이다

파이썬에서 넷을 동시에 돌리는 건 이게 전부다.

findings = await asyncio.gather(
    security(diff), quality(diff), testing(diff), docs(diff)
)

어려운 건 여기가 아니다. 합칠 때다. security()가 예외를 던지면 위 줄이 어떻게 되는지가 이 레슨의 절반이다.

gather()의 두 얼굴 — 공식 문서 그대로

"If return_exceptions is False (default), the first raised exception is immediately propagated to the task that awaits on gather(). Other awaitables in the aws sequence won't be cancelled and will continue to run."

"If return_exceptions is True, exceptions are treated the same as successful results, and aggregated in the result list."
— Python 공식 문서, asyncio — Coroutines and Tasks

굵게 표시한 부분이 함정이다. 기본값에서 하나가 터지면 예외는 즉시 위로 튀는데, 나머지 셋은 취소되지 않는다. 계속 돈다. 결과를 받을 사람이 없는 채로.

LLM 호출이니까 그 셋은 토큰을 계속 태운다. 그리고 아무도 그 결과를 안 읽는다. "에러 났으니 다 멈췄겠지"는 틀린 그림이다.

방식하나가 터지면나머지는
gather() 기본 예외가 즉시 위로 튄다 안 죽는다. 계속 돌며 토큰을 쓴다
gather(return_exceptions=True) 예외가 결과 리스트의 값이 된다 끝까지 기다린다. 순서도 유지
TaskGroup ExceptionGroup으로 묶여 나온다 취소된다. 문서: "the remaining tasks in the group are cancelled"

셋 다 "옳은" 게 아니라 서로 다른 실패 정책이다. "하나라도 실패하면 전부 무의미하다"면 TaskGroup이 맞고, "셋이라도 건지고 싶다"면 return_exceptions=True가 맞다. 우리는 후자다 — 보안 관점이 죽어도 나머지 셋의 지적은 여전히 값이 있다.

asyncio.gather()를 기본값으로 쓰다가 하나가 예외를 던졌다. 나머지 셋은?

  1. 즉시 취소되고 정리된다
  2. 취소되지 않고 계속 돈다
  3. 예외 하나로 묶여서 온다
  4. 마지막 하나만 살아남는다

3. return_exceptions=True로도 거짓말은 안 없어진다

여기가 이 레슨의 심장이다. 위 표에서 답을 골랐으니 이제 안전할까?

먼저 gather()가 돌려주는 것부터 정확히 보자. 이건 그냥 리스트가 아니라 자리가 정해진 4칸짜리 상자다. 순서가 입력 순서 그대로라서 칸 번호가 곧 에이전트 이름이다. 

results = await asyncio.gather(*agents, return_exceptions=True)

results = [ Exception,   [f1, f2],   [f3],      []    ]
              ↑            ↑          ↑         ↑
           security     quality    testing     docs
           (죽음)       (2개 찾음)  (1개)    (봤는데 없음)

이 상자를 보면 전부 알 수 있다. 그런데 여기서 걸러내면:

findings = []
for r in results:
    if isinstance(r, Exception):
        continue                  ← 실패를 여기서 조용히 버린다
    findings.extend(r)

# findings = [f1, f2, f3]   ← 안 터진다. 잘 도는 것처럼 보인다.

return {"findings": findings}

같은 코드를 한 줄로 쓰면 [f for r in results if not isinstance(r, Exception) for f in r]다. 압축하면서 저 continue가 눈에서 사라진다 — 그게 이 절이 위험한 이유의 절반이다.

프로그램은 안 죽는다. 그런데 칸이 사라졌다. 종이 3장만 남는다. 넷이 봤는지 셋이 봤는지 그 리스트 안에는 안 적혀 있다.

결정적인 건 상자의 첫 칸과 마지막 칸이다.

실제로 일어난 일findings 에 보탠 것
security죽어서 못 봤다없음
docs다 보고 문제 없다없음

둘이 기여한 게 똑같이 "없음"이다. 그래서 필터를 지나고 나면 이 둘은 물리적으로 구분 불가능해진다. 맨 앞의 "빈 리스트는 두 가지 뜻"이 추상적인 말이 아니라 바로 이 코드에서 벌어지는 일이다.

예외를 받는 것과 그 사실을 하류에 전달하는 것은 다른 일이다.
isinstance(r, Exception)으로 걸러낸 순간, 실패 정보는 그 if 문 안에서 죽는다.

그래서 팬인(fan-in)에서 넘겨야 할 것은 findings 하나가 아니다. 누가 봤는지를 같이 넘겨야 한다 — 이걸 커버리지(coverage)라고 부르자. 

return {
    "findings":  findings,
    "completed": ["quality", "testing", "docs"],
    "failed":    ["security"],   ← 이게 없으면 게이트는 판단할 수 없다
}

이제 게이트가 물어볼 수 있다. "critical이 없다"가 넷이 다 보고 없는 건가, 셋만 보고 없는 건가?" 앞의 것만 자동 게시로 보낸다.

이미 자리가 파여 있다 migrations/004_truth.sql의 reviews 테이블에 status(어디쯤 있나)와 failed_agents TEXT[](누가 죽었나)를 따로 둔 게 정확히 이걸 위해서다. partial과 auto_posted가 다른 값인 이유가 이 절 전체다.

스키마를 쓸 때는 "언젠가 필요하겠지"였는데, 지금 그 언젠가가 왔다.

4. 타임아웃 — 조용한 멈춤을 시끄러운 실패로

지금까지는 터지는 실패만 봤다. 더 나쁜 게 있다. 안 터지는 실패다.

security()가 LLM에 요청을 보냈는데 응답이 안 온다. 에러도 안 난다. 그냥 조용하다. 파이썬 입장에서 이건 완벽하게 정상인 상태다 — 네트워크 응답을 기다리는 중일 뿐.

그러면 gather()는 어떻게 될까. 영원히 안 끝난다. 셋은 이미 끝났는데 하나를 기다리며 계속 서 있다.

이건 데드락이 아니다. 데드락은 A가 B를 기다리고 B가 A를 기다리는 순환이다. 여기엔 순환이 없다 — 애그리게이터가 노드를 기다릴 뿐, 노드는 아무도 안 기다린다. 그래서 어떤 데드락 탐지기도 이걸 못 잡는다. 잡을 게 없으니까.

증상은 하나다: DB에 status = 'running'인 리뷰가 영원히 남는다.

실패는 시끄럽다 — 스택 트레이스가 뜨고 로그가 남는다. 멈춤은 조용하다. 아무 일도 안 일어나는 게 증상이니까.

그래서 타임아웃이 필요하다. 타임아웃은 성능 장치가 아니라 "조용한 멈춤을 시끄러운 실패로 번역하는 장치"다. 시간이 지났다는 사실 자체를 사건으로 바꾼다. 

async with asyncio.timeout(30):
    result = await security(diff)

"If long_running_task takes more than 10 seconds to complete, the context manager will cancel the current task and handle the resulting CancelledError internally, transforming it into a TimeoutError which can be caught and handled."
— Python 공식 문서, asyncio — Timeouts

TimeoutError가 되는 순간 이건 3절에서 다룬 평범한 예외가 된다. failed: ["security"]에 이름이 올라가고, 게이트가 판단할 수 있는 재료가 된다. 타임아웃의 값어치는 "빨리 끝내는 것"이 아니라 "판단 가능한 것으로 만드는 것"이다.

LLM이 응답을 영영 안 주는데 타임아웃이 없다. 무슨 일이 생기나?

  1. 데드락이 나서 워커가 멈춘다
  2. 에러가 나서 노드가 죽는다
  3. 대기 상태로 조용히 남는다
  4. 다른 노드가 대신 진행한다

5. 막다른 길 없음 — 입력이 0개일 때

넷이 다 죽었다고 하자. 애그리게이터가 받는 findings는 빈 리스트다.

overall = max(f.confidence for f in findings)
# ValueError: max() arg is an empty sequence

애그리게이터가 죽는다. 그러면 그래프가 게이트까지 도달하지 못한다. 리뷰는 running에 멈춘다. 4절의 증상과 똑같은 모양인데 원인이 정반대다.

실패를 다루는 코드가 실패하면,
실패를 다룰 곳이 사라진다.

영상이 "막다른 길 없음(no dead ends)"이라고 부르는 요구가 이거다 [01:21:48]. 모든 경로가 어딘가에 도착해야 한다.

사고방식을 바꿔야 한다. 입력 0개는 예외 상황이 아니라 정상 입력의 하나다. 빈 findings를 받았을 때의 올바른 동작은 죽는 게 아니라 status='failed'로 도착하는 것이다. 그것도 결과다 — "볼 게 없었다"를 사람에게 정직하게 말하는 결과.

6. LangGraph 함정 — superstep은 트랜잭션이다

M5는 LangGraph로 이 그래프를 짠다. 여기서 예상을 뒤집는 문장이 하나 있다.

"LangGraph executes nodes within supersteps, meaning that while parallel branches are executed in parallel, the entire superstep is transactional. If any of these branches raises an exception, none of the updates are applied to the state (the entire superstep errors)."
— LangChain 공식 문서, Use the graph API

읽어보면 3절보다 더 나쁘다. security가 터지면 성공한 quality·testing·docs의 결과까지 state에 하나도 안 남는다. 셋이라도 건지려던 계획이 통째로 날아간다.

그래서 결론이 나온다. 예외가 노드 밖으로 나가면 안 된다. 

async def security_node(state):
    try:
        async with asyncio.timeout(30):
            return {"findings": await security(state["diff"]),
                    "completed": ["security"]}
    except (Exception, TimeoutError):
        return {"findings": [], "failed": ["security"]}
        ↑ 예외가 아니라 "값"으로 나간다. superstep 이 안 터진다.

실패를 예외로 전파하지 않고 데이터로 표현하는 것. 3절의 failed: [...]가 왜 그 모양이어야 했는지가 여기서 완결된다.

그리고 각 노드가 리스트를 덧붙이려면 state에 리듀서(reducer)가 필요하다. 안 걸면 뒤에 끝난 노드가 앞의 값을 덮어쓴다 — 넷이 돌았는데 findings가 하나만 남는다. 

class ReviewState(TypedDict):
    findings:  Annotated[list, operator.add]   ← 이어붙인다
    failed:    Annotated[list, operator.add]
    diff:      str                              # 아무도 안 고치니 리듀서 불필요

LangGraph에서 병렬 브랜치 하나가 예외를 던졌다. 성공한 나머지의 state 업데이트는?

  1. 성공한 것만 반영되어 남는다
  2. 하나도 반영되지 않고 끝난다
  3. 재시도 후에 자동 병합된다
  4. 리듀서가 빈 값으로 채운다

정리 — 다섯 문장

#알게 된 것
1병렬은 서로의 출력을 안 쓸 때만 안전하다. 아니면 얻는 건 속도가 아니라 충돌
2gather() 기본값은 나머지를 취소하지 않는다. 고아 태스크가 토큰을 태운다
3예외를 받는 것과 하류에 전달하는 것은 다르다. findings 옆에 failed를 동봉해야 한다
4타임아웃은 성능 장치가 아니라 조용한 멈춤을 판단 가능한 사건으로 바꾸는 번역기
5LangGraph superstep은 트랜잭션이다. 예외를 노드 밖으로 내보내면 성공한 결과까지 날아간다

우리 코드로 어디에 떨어지나

아직 아무것도 없다. M5에서 만들 것이다: backend/orchestration/engine.py(추상)와 backend/orchestration/langgraph_engine.py(구현).

착지점만 이미 파여 있다 — migrations/004_truth.sql의 status와 failed_agents. 3절에서 만든 {"findings": ..., "failed": [...]}가 그대로 저 두 컬럼으로 들어간다.

M5 완료 판정 ③이 이 레슨 전체의 시험이다: "한 노드를 일부러 무한 대기시켜도 타임아웃 후 애그리게이터가 나머지로 진행한다."

그리고 그때 확인할 것 하나 더 — 진행했다는 사실만 보지 말 것. 결과에 failed: ["security"]가 실제로 들어 있는지까지 봐야 한다. Lesson 05에서 "막히는 것만 보면 무엇을 막았는지 모른다"고 했던 것과 같은 함정이다.

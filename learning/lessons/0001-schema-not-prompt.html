Lesson 01 · M0 · backend/agents/base.py

JSON을 부탁하지 말고,
스키마로 강제하라

LLM에게 형식을 요청하는 것과, 형식을 강제하는 것은 다른 일이다.

이 레슨이 주는 것

방금 schema.py에서 Finding과 ReviewResult를 만들었다. 그런데 그 pydantic 모델이 LLM에게 어떻게 전달되는지는 아직 안 봤다. 이 레슨이 그 연결을 만든다. 끝나면 base.py에서 무슨 일이 일어나는지 알고 시작할 수 있다.

먼저, 부탁이 왜 실패하나

LLM API를 처음 쓰면 자연스럽게 이렇게 한다:

# 이렇게 하지 마라
prompt = """이 diff를 리뷰하고 JSON으로 답해줘.
형식: [{"severity": "...", "line": 12, "confidence": 0.9}]"""

resp = client.chat.completions.create(model="...", messages=[...])
findings = json.loads(resp.choices[0].message.content)  # 💥

이게 깨지는 방식이 한두 가지가 아니다:

모델이 보낸 것결과
```json\n[...]\n```코드펜스가 붙어 json.loads 실패
물론이죠! 리뷰 결과입니다: [...]인사말이 앞에 붙어 실패
{"findings": [...]}배열을 부탁했는데 객체로 감싸서 옴
"confidence": "high"숫자를 부탁했는데 문자열이 옴
"severity": "Critical"대문자 — 게이트의 == "critical"이 조용히 빗나감
핵심

프롬프트로 형식을 요청하는 건 부탁이다. 모델은 대체로 들어주지만, 100번 중 3번은 안 들어준다. 그리고 그 3번이 매번 다른 방식으로 깨진다. 파싱 코드에 try/except를 아무리 붙여도 새로운 깨짐이 계속 나온다.

강제하는 방법

OpenAI SDK의 parse()에 pydantic 모델을 넘기면, 부탁이 아니라 제약이 된다. 

from backend.agents.schema import ReviewResult

completion = client.chat.completions.parse(
    model="gpt-4o-2024-08-06",
    messages=[...],
    response_format=ReviewResult,   # ← 여기
)

result = completion.choices[0].message.parsed   # ReviewResult 인스턴스

이 한 줄에서 세 가지 일이 일어난다:

  1. SDK가 pydantic 모델을 JSON schema로 변환한다. Literal["critical", ...]은 enum이 되고, ge=0.0은 minimum: 0.0이 된다.
  2. 서버가 그 스키마를 디코딩 단계에서 강제한다. 프롬프트로 타이르는 게 아니라, 토큰을 생성할 때 스키마에 맞지 않는 토큰의 확률을 0으로 만든다. 그래서 구조적으로 틀린 출력이 나올 수 없다.
  3. SDK가 응답을 다시 pydantic 모델로 파싱해서 돌려준다. json.loads도, 코드펜스 벗기기도 없다.

프롬프트는 무엇을 쓸지를 말하고,
스키마는 무엇을 쓸 수 없는지를 막는다.

그런데 description은 여전히 프롬프트다

여기가 이 레슨에서 가장 중요한 지점이다. 스키마로 변환될 때 Field(description=...)도 같이 실려 간다. 

# schema.py 에서 쓴 것
confidence: float = Field(ge=0.0, le=1.0, description="이 지적이 사실일 확률...")

# 서버로 가는 JSON schema
"confidence": {
  "type": "number",
  "minimum": 0.0,          ← 강제됨
  "maximum": 1.0,          ← 강제됨
  "description": "이 지적이 사실일 확률..."   ← 모델이 읽는 지시문
}

그래서 두 종류가 한 필드에 공존한다. 제약은 물리적으로 막고, description은 설득한다.

강제되나틀리면
type, enum, minimum 예 — 위반 불가애초에 생성이 안 됨
description 아니오 — 읽고 참고할 뿐그럴듯한 값이 조용히 들어옴
이미 겪은 것

description="자신감?"이라고 썼을 때 confidence가 전부 0.9로 굳는 이유가 이거다. 범위(0~1)는 스키마가 막아주지만, 그 안에서 어떤 값을 고를지는 순전히 description이 결정한다. M0 완료 판정이 "confidence가 항상 같은 값이면 실패"인 것도 같은 이유다 — 그건 형식의 문제가 아니라 내용의 문제라서, 스키마가 잡아줄 수 없다.

우리 코드에 남은 흔적

schema.py 맨 아래를 다시 보자:

class ReviewResult(BaseModel):
    findings: list[Finding]

왜 list[Finding]을 그냥 안 쓰고 감쌌을까? JSON schema의 최상위는 객체여야 하기 때문이다. 배열을 최상위로 주면 API가 거부한다. 그래서 리스트를 반환하고 싶으면 항상 한 겹 감싸야 한다. 이건 우리 설계 취향이 아니라 규격이다.

회상 연습

parse()에 pydantic 모델을 넘기면 무엇이 보장되나?

  1. 응답 필드 값이 사실과 부합한다
  2. 응답 구조가 스키마와 일치한다
  3. 응답 내용이 매번 동일하게 온다
  4. 응답 속도가 일정하게 유지된다

Field(description=...)에 쓴 문장은 어디로 가나?

  1. 코드에만 남고 전송되지 않는다
  2. 스키마에 실려 모델에 전달된다
  3. 헤더에 붙어 서버에 기록된다
  4. 응답에 그대로 복사돼 돌아온다

여기서 이어지는 것

스키마가 형식은 보장하지만 내용은 보장하지 않는다는 사실이, 이 프로젝트 후반부의 설계를 통째로 결정한다.

  • M0 완료 판정 — confidence가 분포하는지 눈으로 확인해야 하는 이유
  • M6 애그리게이터 — rationale이 인용한 코드가 실제 diff 안에 있는지 문자열로 대조 (docs/04-book-reading-plan.md의 G1)
  • M8 게이트 — 형식이 맞는 finding도 틀릴 수 있으니, 확신이 낮으면 사람에게 넘긴다. 이 시스템의 존재 이유가 정확히 여기다

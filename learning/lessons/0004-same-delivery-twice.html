Lesson 04 · M1 · backend/queue/router.py

같은 배달이
두 번 왔을 때

한 번만 일어나야 하는 일을, 여러 번 와도 한 번만 일어나게 만드는 법.

이 레슨이 주는 것

Lesson 03에서 가짜 요청을 막았다. 이번엔 진짜인데 두 번 온 요청이다. 서명은 완벽히 통과한다. 그래도 처리하면 안 된다 — 같은 PR에 리뷰 코멘트가 두 번 붙으니까. 끝나면 INV-2가 왜 불변식인지, 그리고 우리 dedup이 어디까지만 버티는지 알게 된다.

먼저 — 영상의 전제 하나가 틀렸다

이 프로젝트 문서 여러 곳에 "GitHub은 같은 배달을 재시도한다"고 적혀 있다. 이번에 1차 출처를 확인했더니 정반대였다:

"GitHub does not automatically redeliver failed webhook deliveries."
— GitHub Docs, Handling failed webhook deliveries

같은 문서에서 10초라는 수치도 확정됐다 — 실패는 "your server is down or takes longer than 10 seconds to respond"일 때다. 영상이 [00:03:06]과 [01:31:39]에서 두 가지 수치를 말하며 흔들렸던 그 값이다.

그럼 INV-2는 폐기해야 하나? 아니다. 중복이 오는 경로가 다를 뿐이다.

중복의 출처일어나나
GitHub의 자동 재시도아니오 — 1차 출처가 명시적으로 부정
사람이 UI/API로 누르는 수동 재배달예 — 디버깅할 때 실제로 자주 한다
우리 쪽 큐의 재시도 (M4 ARQ)예 — 워커가 죽으면 잡이 다시 실행된다
같은 PR에 push가 이어질 때예 — 다른 배달이지만 리뷰는 중복이다(M8의 문제)

오히려 더 무서운 사실이 하나 딸려온다. 자동 재시도가 없다는 건 우리가 10초 안에 답하지 못하면 그 이벤트는 영원히 사라진다는 뜻이다. 큐를 넣는 이유가 "느려도 되니까"가 아니라 "안 넣으면 유실된다"로 바뀐다.

멱등성 — 여러 번 해도 한 번

멱등(idempotent)이란 몇 번을 실행해도 결과가 같다는 뜻이다. 

엘리베이터 버튼   여러 번 눌러도 한 번 온다        멱등
자판기 버튼      누른 만큼 나온다                멱등 아님

웹훅 처리는 태생이 자판기다. 두 번 오면 두 번 리뷰하고, 코멘트가 두 개 붙는다. 이걸 엘리베이터로 바꾸는 게 이번 파트의 일이고, 방법은 하나다 — 이미 본 배달인지 기억해두고, 봤으면 버린다.

기억의 열쇠: delivery ID

GitHub은 배달마다 X-GitHub-Delivery 헤더에 고유 ID를 담아 보낸다. REST API의 delivery 객체를 보면 필드가 이렇게 갈려 있다: 

{
  "id":         12345678,        // 시도 하나하나
  "guid":       "a1b2c3-...",    // 이벤트 하나 (헤더로 오는 값)
  "redelivery": true,            // 재배달인가
  ...
}

아직 확정 못 한 것: 재배달이 guid를 그대로 쓰는지 공식 문서에 문장으로 적혀 있지 않다. 다만 id와 guid가 따로 있고 redelivery 플래그가 별도로 존재한다는 구조는 "guid = 이벤트, id = 시도"라는 해석을 강하게 뒷받침한다.

추측을 사실처럼 쓰지 않는다. 구현은 이 해석 위에 올리되, M1이 끝나면 실제 재배달을 한 번 쏴서 눈으로 확인한다. 문서보다 관측이 세다.

GitHub이 자동 재시도를 하지 않는다면, 우리 인그레스에 무엇이 달라지나?

  1. 멱등성 처리가 더는 필요 없어진다
  2. 실패해도 나중에 다시 오니 안전하다
  3. 응답 코드를 아무거나 써도 무방하다
  4. 늦게 답하면 이벤트가 영구 유실된다

함정 ①: 확인과 기록 사이의 틈

순진하게 쓰면 이렇게 된다:

if delivery_id in seen:        # ① 확인
    return
process(payload)               # ② 처리
seen.add(delivery_id)          # ③ 기록

①과 ③ 사이가 벌어져 있다. 같은 배달 두 개가 거의 동시에 오면 둘 다 ①을 통과하고 둘 다 ②를 실행한다. 코멘트가 두 개 붙는다.

고치는 방향은 "확인과 기록을 하나의 동작으로"다. 파이썬 set에는 그런 연산이 있다 — 넣으면서 "새것이었는지"를 같이 알려주는 방식으로 쓸 수 있다. 찾아볼 것: set.add()의 반환값은 무엇이고, len()은 그 전후로 어떻게 변하나.

함정 ②: 기억은 무한하지 않다

seen이 계속 자라면 프로세스가 오래 살수록 메모리를 먹는다. 그렇다고 작게 잡으면 오래된 재배달을 못 걸러낸다. 얼마나 오래 기억할 것인가가 판단이고, 이건 M4에서 Redis TTL로 넘어간다.

그리고 M1의 인메모리 dedup은 프로세스 재시작을 못 넘긴다. 서버를 껐다 켜면 seen이 비고, 재배달이 전부 통과한다. 이건 버그가 아니라 알고 하는 타협이다 — 브로커 의존성을 M1에 끌고 오는 게 "인그레스 계약까지"라는 이 마일스톤의 범위를 넘기 때문이다 [02:44:28]. 알고 미룬 것과 까먹은 것은 다르다. 그래서 CURRENT.md에 적어둔다.

인메모리 dedup 이 M1 에서 충분하다고 보는 근거는?

  1. 재시작을 넘어서도 상태가 남는다
  2. 이 마일스톤의 범위가 거기까지다
  3. 동시 요청에도 안전하게 동작한다
  4. 메모리를 무제한 쓸 수 있어서다

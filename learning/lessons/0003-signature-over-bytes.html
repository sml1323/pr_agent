같은 뜻의 JSON 두 개는 서로 다른 서명을 갖는다. 이 한 문장이 M1의 첫 함정 전부다.

이 레슨이 주는 것

Lesson 02에서 diff를 못 믿는 법을 배웠다. 그런데 그 diff가 우리 서버에 들어오는 문 자체는 아직 잠기지 않았다. 이번엔 그 문 — POST /webhook — 이다. 끝나면 security.py의 검증 함수를 왜 그 순서로 써야 하는지 알게 된다.

전체 그림에서 ①. 아직 큐도 DB도 없다. 문 하나만 단다.

먼저: 서명이 뭘 증명하나

GitHub와 우리는 공유 비밀(secret) 하나를 미리 나눠 갖는다. GitHub은 요청을 보낼 때 HMAC-SHA256(secret, body)를 계산해 X-Hub-Signature-256 헤더에 담는다. 우리는 같은 계산을 다시 해서 맞춰본다.

맞으면 증명되는 건 딱 하나 — 이 요청을 만든 쪽이 그 비밀을 갖고 있다. "내용이 참이다"도 "안전하다"도 아니다. 출처만 증명한다. 그래서 Lesson 02의 트러스트 바운더리가 여전히 필요하다. 두 경계는 다른 것을 막는다.

경계막는 것어디
HMAC 서명 (INV-1)아무나 보낸 가짜 요청webhook/security.py
untrusted diff (Lesson 02)진짜 요청 안의 악성 내용agents/base.py

GitHub이 보낸 진짜 PR 안에 인젝션 주석이 들어있는 건 완벽히 정상적인 시나리오다. 서명은 통과한다. 그게 통과해야 맞다.

함정 ①: 파싱하면 서명이 죽는다

FastAPI에서 제일 자연스러운 코드는 이거다. 그리고 절대 안 맞는다. 

payload = await request.json()          # dict 가 됐다
body = json.dumps(payload).encode()     # 다시 바이트로... 같은 바이트가 아니다
mac = hmac.new(secret, body, hashlib.sha256)

HMAC은 바이트 열을 먹는다. 한 글자만 달라도 결과가 완전히 달라진다. 그런데 json.dumps()는 원본을 복원하지 못한다:

GitHub이 보낸 원본json.dumps() 결과
{"a":1,"b":2}{"a": 1, "b": 2} ← 공백
{"b":2,"a":1}키 순서가 dict 삽입 순서로 고정
"café""café" ← 이스케이프 풀림

사람 눈엔 같은 JSON이고 == 로 비교하면 같은 dict다. 바이트로는 다른 문서다.

정답: body = await request.body() — 손대지 않은 raw bytes. 서명 계산에도, 그 뒤 json.loads(body) 에도 이 값 하나를 쓴다.

함정 ②: == 로 비교하면 안 된다

파이썬의 ==는 문자열을 앞에서부터 비교하다 다른 글자를 만나면 즉시 멈춘다. 그래서 첫 글자가 틀린 서명은 아주 조금 빨리 거부된다. 공격자가 같은 요청을 수만 번 보내며 응답 시간을 재면, 그 미세한 차이로 서명을 한 글자씩 알아낼 수 있다(타이밍 공격). 

hmac.compare_digest(expected, received)   # 항상 전체를 비교한다

GitHub 공식 문서도 명시적으로 이걸 요구한다 — "timing-safe methods like secure_compare or crypto.timingSafeEqual" (Validating webhook deliveries).

웹훅 핸들러에서 await request.body() 대신 await request.json()을 쓰면 생기는 일은?

  1. 본문 파싱이 실패해서 예외가 난다
  2. 페이로드 내용이 조용히 변형된다
  3. 정상 요청도 서명이 안 맞게 된다
  4. 타이밍 공격에 취약한 상태가 된다

함정 ③: 400인가 403인가 500인가

여기서 출처끼리 충돌한다. 그대로 보여준다.

상황GitHub 공식 예제이 프로젝트 (INV-1)
서명 불일치403400
서명 통과 + 깨진 JSON언급 없음400 (500 절대 아님)

GitHub 문서의 파이썬 예제는 HTTPException(status_code=403, ...) 을 쓴다. 우리 docs/invariants.md는 400으로 획일화하기로 했다. 근거는 "실패 이유와 무관하게 항상 같은 응답" — 403과 400을 갈라 쓰면 공격자가 응답만 보고 "헤더는 맞췄고 서명만 틀렸구나"를 알게 된다.

둘 다 방어 가능한 선택이다. 중요한 건 하나로 고정하고 그 이유를 적어두는 것 (03-build-plan.md가 ADR로 남기라고 한 이유).

진짜 체크포인트는 두 번째 줄이다. 영상에서 빌더 에이전트는 M1을 "다 됐다"고 선언했는데, 독립 검증자가 깨진 JSON에 500 크래시를 잡아냈다 [02:38:39].
논리: 서명을 통과했다 = 상대가 비밀키를 가진 인증된 호출자다. 인증된 호출자가 보낸 잘못된 본문은 클라이언트 잘못(4xx)이지 서버 잘못(5xx)이 아니다. 500을 뱉으면 서버 모니터링에 헛경보가 뜨고, 진짜 장애를 그 소음에 묻어버린다.

서명은 맞는데 본문이 {"pull_re 처럼 잘린 JSON이면 뭘 돌려주나?

  1. 500 — 서버가 처리에 실패했다
  2. 400 — 보낸 쪽의 본문이 틀렸다
  3. 403 — 인증되지 않은 요청이다
  4. 200 — 일단 받았다고 알린다

그래서 순서가 이렇게 된다

body = await request.body()        # ① raw bytes 를 먼저 잡는다
verify(body, signature_header)     # ② 서명. 실패 → 400, 여기서 끝
if event != "pull_request": ...    # ③ 관심 없는 이벤트 버리기
payload = json.loads(body)         # ④ 이제야 파싱. 실패 → 400
enqueue(...)                       # ⑤ 큐에 넣고
return 200                         # ⑥ 즉시 답한다

검증이 파싱보다 먼저다. 반대로 하면 "서명을 안 본 요청"에 대해 파싱 로직이 먼저 도는 표면이 생긴다. 그 파서가 공격 대상이 된다.

⑤와 ⑥이 붙어있는 이유는 시간이다. GitHub은 ack를 아주 빨리 기대하는데 (영상의 두 수치: ~10초 [00:03:06] / ~10-12초, 화자가 불확실하다고 밝힘 [01:31:39]) LLM 리뷰는 30~90초가 걸린다. 핸들러 안에서 리뷰하면 반드시 타임아웃이다. 이건 취향이 아니라 외부 제약이고, 그래서 M1에 큐 스텁이라도 반드시 들어간다.

아직 확인 못 한 것

재배달(redelivery) 시 X-GitHub-Delivery GUID가 같은 값인가?
GitHub 공식 문서 세 곳(validating deliveries · webhook events and payloads · redelivering webhooks)을 찾아봤는데 명시된 문장이 없다. 파생 블로그 말고 1차 출처에서 아직 못 찾았다.

이게 왜 중요하냐면 — INV-2(멱등성)가 통째로 여기에 걸려 있다. GUID가 재배달마다 새로 발급된다면, delivery ID로 만든 dedup 키는 중복 리뷰를 못 막는다. 같은 PR에 코멘트가 두 번 붙는다.

M1을 구현하면서 실제 재배달을 한 번 쏴보고 눈으로 확인할 것. 문서보다 관측이 세다.

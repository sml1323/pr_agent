Lesson 10 · M5-5 · backend/orchestration/langgraph_engine.py

타임아웃은
취소가 아니다

"5초 뒤 포기"는 기다리는 쪽이 포기하는 것이다. 일하는 쪽은 계속 돈다.

09 가 남긴 구멍 Lesson 09 에서 터지는 것을 값으로 바꿨다. raise 하면 except 가 받아 failed_agents 에 이름이 남는다.

그런데 안 터지고 안 끝나는 것은 except 가 받을 게 없다. try 안에서 영원히 안 나온다. M5-4 실측이 딱 여기서 멈췄다.

왜 이게 M5 에서 제일 위험한가

Lesson 08 에서 확인한 것 — superstep 은 배리어다. 넷 중 셋이 0.8초에 끝나도, 남은 하나가 안 끝나면 그 층이 안 닫힌다. aggregate 는 영원히 안 선다. 

security  ██████ 0.6s  끝
quality   ████   0.4s  끝
docs      ███    0.3s  끝
testing   ███████████████████████████...   ← 이 하나 때문에
                                            aggregate 는 시작조차 못 한다
예외는 한 노드를 죽인다.
무한 대기는 그래프 전체를 세운다.

그리고 더 나쁜 건 이게 실패로 보이지도 않는다는 것이다. 로그도 없고, 에러도 없고, failed_agents 도 비어 있다. Lesson 06 의 "빈 것의 뜻 셋" 중 ③ — 돌고 있는데 안 끝남 — 이 자리다.

실측 ① — 타임아웃을 걸어도 일은 안 멈춘다

가장 흔한 첫 시도부터 보자. 스레드에 던지고 timeout 을 주고 기다린다. 

fut = executor.submit(slow)      # slow 는 2초 걸린다
fut.result(timeout=0.5)          # 0.5초만 기다린다
[0.50초] TimeoutError — 기다리기를 포기했다
  fut.cancel() → False   (False = 취소 못 함)
  0.5초 시점  done=[]
  2.5초 시점  done=['나 아직 살아있다']   ← 포기한 뒤에도 끝까지 돌았다

1차 출처 "Attempt to cancel the call. If the call is currently being executed or finished running and cannot be cancelled then the method will return False, otherwise the call will be cancelled and the method will return True."
— Python — concurrent.futures.Future.cancel

cancel() 이 성공하는 건 아직 시작 안 한 일뿐이다. 이미 돌고 있으면 파이썬은 그걸 멈출 방법이 없다 — 스레드에는 kill 이 없다. 같은 문서가 더 세게 말한다:

1차 출처 "Regardless of the value of wait, the entire Python program will not exit until all pending futures are done executing."
— Python — Executor.shutdown

timeout 은 기다림에 거는 것이지
실행에 거는 것이 아니다.

실측 ② — LangGraph 는 이걸 알고 아예 거부한다

LangGraph 에는 노드별 타임아웃이 있다. 우리 노드에 걸어봤다: 

graph.add_node("slow", slow_sync, timeout=0.5)   # slow_sync 는 def (동기)
graph.compile()
ValueError: Node timeouts are only supported for async nodes
because sync Python execution cannot be safely cancelled in-process.
Node 'slow' is sync.

돌려보기도 전에, 컴파일에서 막혔다. 라이브러리가 우리 대신 거짓말을 거절한 것이다 — 동기 노드에 타임아웃을 받아주면 "걸었으니 안전하다"고 믿게 되는데 실제로는 아무 일도 안 일어난다. Lesson 01 의 사고방식과 같다: 못 지킬 약속은 애초에 안 받는다.

실측 ③ — async 로 바꿔도 안이 막혀 있으면 안 먹는다

그럼 async def 로 바꾸면 되나? 노드는 async 인데 안에서 동기 대기를 하면:

노드 안timeout결과
await asyncio.sleep(3)0.5초0.51초 · NodeTimeoutError ✅
time.sleep(3)0.5초3.02초 · 그냥 성공 💥

같은 timeout=0.5 인데 아래 줄은 3초를 다 채우고 성공으로 끝났다. 에러도 경고도 없다. LangGraph 소스가 이걸 미리 적어뒀다:

1차 출처 "Timeouts rely on asyncio cancellation. If your node uses synchronous time.sleep() or other CPU-bound work that blocks the GIL, the timeout will not be fired until after the event loop has been released."
— langgraph.types.TimeoutPolicy 독스트링 (설치된 패키지에서 직접 읽음)

타임아웃은 협조를 요구한다. 일하는 쪽이 중간에 손을 놓아주는(await) 지점이 있어야 취소가 끼어든다. 손을 안 놓으면 아무도 못 끼어든다.

진짜 판단 — 타임아웃을 어느 층에 거나

층이 셋이다. 층이 다르면 실패의 모양이 다르다.

어디느린 하나가 생기면
①invoke() 바깥넷이 같이 죽는다. 살아남은 셋의 결과도 버려진다
②노드 밖 (LangGraph timeout=)예외가 밖으로 나간다 → 우리 except 가 못 받는다
③노드 안 (호출 자체에)예외가 try 안에서 난다 → 값으로 바뀐다 ✅

②를 실제로 돌려봤다. 느린 노드 하나 + 빠른 노드 하나, 느린 쪽에만 타임아웃: 

0.51초 · NodeTimeoutError: Node 'slow' exceeded its run timeout of 0.500s

ainvoke() 가 터졌다. 빠른 노드는 이미 끝났는데 결과를 못 받는다. _run_specialist 의 try 는 노드 안에 있고 이 예외는 노드 밖에서 났으니, Lesson 09 에서 공들여 나눈 except 절 둘을 통째로 지나쳐 간다.

노드 밖에서 잰 시간은 노드 안의 값이 될 수 없다.
failed_agents 에 이름을 남기려면 안에서 재야 한다.

이게 G2 다 CURRENT.md 의 최악 시나리오 — "critical 없음"과 "확인 안 됨"을 게이트가 구분 못 하는 것. ①②는 부분 실패를 전체 실패로 승격시킨다. M5-4 에서 어렵게 만든 "셋이 죽어도 하나로 진행한다"가 여기서 도로 무너진다.

그럼 ③은 어떻게 하나 — 이미 준비돼 있다

M6 에서 _call_agent 안이 진짜 HTTP 호출이 된다. HTTP 는 소켓을 닫을 수 있다 — 스레드와 달리 진짜로 멈출 수 있는 대상이다. OpenAI SDK 가 그 손잡이를 이미 노출한다: 

# openai/_constants.py — 설치된 패키지에서 직접 읽음
DEFAULT_TIMEOUT = httpx.Timeout(timeout=600, connect=5.0)
DEFAULT_MAX_RETRIES = 2

⚠️ 기본값을 읽어라 600초 = 10분이다. 웹훅 워커가 10분 동안 한 에이전트를 기다린다는 뜻이고, 이건 사실상 "타임아웃 없음"과 구분이 안 된다. 기본값이 있다는 것과 그 기본값이 우리에게 맞다는 것은 다른 얘기다.

그리고 이 예외의 족보가 Lesson 09 와 정확히 맞물린다: 

OpenAIError
 └── APIError
      └── APIConnectionError
           └── APITimeoutError      # ← M5-4 의 첫 except 가 이미 받는다

M5-4 에서 쓴 except openai.OpenAIError 가 타임아웃도 함께 받는다. 09 에서 "지금 아는 것으로 세운 가설"이라고 했던 게 여기서 이자를 낸다 — 층을 골라 잡았기 때문에 새 실패 종류가 하나 늘어도 코드를 안 고친다.

몇 초로 정하나

숫자를 고르는 건 취향이 아니라 계산이다. 재료가 셋 있다:

재료묻는 것틀리면
정상 응답의 꼬리느린 정상 호출이 몇 초까지 가나짧으면 멀쩡한 응답을 실패로 기록
위에서 정한 예산워커 하나가 리뷰 하나에 몇 초까지 쓰나길면 큐가 밀린다
배리어넷 중 가장 느린 하나가 층 전체 시간노드별 예산 ≠ 합계 예산

우리가 아직 모르는 것 첫 번째 재료가 M5 에 없다. 더미 노드의 0.3~0.8초 는 우리가 만든 숫자지 관측한 숫자가 아니다. 그래서 지금 고르는 값은 잠정치다 — M6 에서 진짜 호출의 지연을 보고 다시 정할 자리다. 중요한 건 지금 맞는 숫자를 찍는 게 아니라 고칠 자리를 한 곳으로 모아두는 것이다.

타임아웃 뒤에 재시도하면 — INV-2 가 걸린다

"포기했다"는 "안 일어났다"가 아니다. 실측 ①에서 본 그대로 — 우리가 포기한 뒤에도 저쪽은 끝까지 돌았다. LLM 호출이면 서버는 이미 답을 만들었고 토큰도 이미 썼다. 우리만 그걸 못 본 것이다. 

클라이언트:  ──기다림──✂ 포기(timeout)      # 여기서 재시도하면?
서버:        ──────────────완료─→ 응답      # 이건 이미 일어났다

그래서 재시도는 같은 일을 두 번 시키는 것일 수 있다. Lesson 04(INV-2)가 웹훅 입구에서 푼 문제와 같은 문제가 LLM 호출 앞에서 다시 나온다. SDK 가 기본으로 max_retries=2 를 하고 있다는 걸 아는 것이 그래서 중요하다 — 우리가 재시도를 안 써도 이미 재시도가 돌고 있다.

우리 코드에 착지

_call_agent() 가 지금은 time.sleep() 이다 — 실측 ③의 아래 줄, 즉 어떤 타임아웃도 안 먹는 모양이다. M5-5 의 일은 그래서 두 가지로 갈린다:

  • 자리를 파는 것 — 타임아웃이 노드 안에서 나서 except 로 흘러가게. M6 에서 SDK 의 timeout= 이 그 자리에 꽂힌다
  • 더미로 증명하는 것 — 지금 안 끝나는 노드를 만들어 놓고, 나머지 셋이 findings 를 들고 done 까지 가는지 눈으로 볼 것

1차 출처 — 이건 꼭 읽을 것

Python — concurrent.futures 의 Future.cancel 두 문장. 여기서 "cannot be cancelled" 를 직접 읽는 게 이 레슨의 절반이다.

나머지 절반은 설치된 패키지 안에 있다. 문서보다 정확하다: 

uv run python -c "
from langgraph.types import TimeoutPolicy
print(TimeoutPolicy.__doc__)
import openai._constants as c
print(c.DEFAULT_TIMEOUT, c.DEFAULT_MAX_RETRIES)
"

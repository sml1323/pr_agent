엣지는 시간을 긋는다

노드는 뭘 하는지 정하고, 엣지는 언제 하는지 정한다. 같은 노드 넷이 배선 하나로 한 층이 되기도, 네 층이 되기도 한다.

07 의 짝 Lesson 07 은 공간이었다 — 값이 어느 칸에 담기나(채널), 한 칸에 둘이 쓰면 어떻게 되나(리듀서).

이번은 시간이다 — 누가 언제 도나. 두 레슨이 합쳐져야 superstep 이 완성된다.

장면부터 — 같은 노드 넷, 배선만 다르게

스페셜리스트 넷이 각자 0.3초 걸린다(LLM 호출 흉내). 그리고 애그리게이터가 결과를 모은다. 노드 코드는 세 경우 모두 한 글자도 안 바꿨다. 엣지만 바꿔서 돌린 실측:

배선시간최종 foundaggregate 가 실행될 때 본 것
팬아웃 + 팬인0.30초4개4개 ✅
체인 (직렬)1.22초4개4개
팬인 빠뜨림0.31초4개0개 💥

세 경우 다 에러가 없다. 그리고 최종 found 는 셋 다 4개다. 끝나고 결과만 보면 셋을 구분할 수 없다.

그런데 하나는 4배 느리고,
하나는 애그리게이터가 빈 것을 보고 판정했다.

두 함정은 정확히 대칭이다

체인팬인 빠뜨림
증상느린데 맞다빠른데 틀리다
잃는 것시간 (에이전트 수에 비례)정확성 — 조용히
언제 들킬까느리다고 누가 말할 때안 들킨다

우리 시스템에서 "빠른데 틀리다"가 어떤 모습인지 그려보면 — 애그리게이터가 findings 를 0개로 보고 전체 확신도를 계산한다. 게이트는 "지적할 게 없음"으로 읽고 자동 통과시킨다. 실제로는 넷이 전부 문제를 찾았는데.

Lesson 06 과 같은 모양 "아무 문제 없음"과 "아무도 안 봄" 이 또 나왔다. 거기선 노드가 죽어서 빈 결과가 됐고, 여기선 배선이 틀려서 빈 결과를 봤다. 증상이 같다 — 빈 것을 정상으로 읽는다.

왜 이렇게 되나 — 엣지가 superstep 을 만든다

공식 정의는 짧다 — "If a node has multiple outgoing edges, all destination nodes execute in parallel during the next superstep." (Graph API — Edges) 

# 팬아웃 — START 에서 나가는 엣지가 넷
g.add_edge(START, "security")
g.add_edge(START, "quality")     → 넷이 같은 superstep
g.add_edge(START, "testing")
g.add_edge(START, "docs")

# 체인 — 각 노드에서 나가는 엣지가 하나씩
g.add_edge(START, "security")
g.add_edge("security", "quality")   → superstep 이 넷
g.add_edge("quality", "testing")
g.add_edge("testing", "docs")

"병렬로 돌려라"라는 명령은 어디에도 없다. 나가는 엣지를 여러 개 그은 것뿐이고, 병렬은 그 결과다. 그래서 실수로 직렬이 돼도 아무도 안 알려준다 — 문법적으로 완벽히 정상이니까.

팬인은 공짜로 기다려준다

g.add_edge("security", "aggregate")
g.add_edge("quality",  "aggregate")   → 넷 다 끝나야 aggregate 시작
g.add_edge("testing",  "aggregate")
g.add_edge("docs",     "aggregate")

들어오는 엣지가 여럿이면 LangGraph 가 전부 끝날 때까지 기다린다. 따로 "기다려라"를 쓸 필요가 없다. 반대로 이 엣지를 안 그으면 기다릴 이유가 없어져서 aggregate 가 넷보다 먼저 돌아버린다 — 위 표의 세 번째 줄이 그거다.

층은 배리어다 — 엣지는 "누구를 기다리나"를 정하지 않는다

여기서 거의 모두가 한 번 틀린다. 스페셜리스트 넷 중 둘만 aggregate 로 잇고, 나머지 둘은 END 로 보낸 뒤 그 둘을 5배 느리게 만들었다: 

security  끝남  t=0.11초
quality   끝남  t=0.11초
testing   끝남  t=0.51초     # aggregate 와 엣지로 안 이어져 있다
docs      끝남  t=0.51초
aggregate 시작 t=0.51초  ← 이 순간 found 4개

aggregate 는 자기와 이어진 둘(0.11초)이 아니라 층 전체(0.51초)를 기다렸다. 그리고 엣지가 없는 둘의 결과까지 봤다.

엣지는 어느 층에 서나를 정한다.
누구를 기다리나가 아니다 — 층에 서면 그 층 전체와 운명을 같이 한다.

값이 엣지를 타고 흐르는 게 아니라는 뜻이기도 하다. 값은 채널에 있고 (Lesson 07), 층이 끝날 때 통째로 커밋된다. 엣지는 순서만 정한다.

그래서 M5-5 에 타임아웃이 필요하다 배리어라면 — 한 노드가 안 끝나면 그래프 전체가 영원히 멈춘다. 나머지 셋이 다 끝나도 소용없다.

03-build-plan.md M5 완료 판정 ③은 "한 노드를 무한 대기시켜도 애그리게이터가 나머지로 진행"을 요구한다. 배리어를 뚫는 방법은 하나뿐이다 — 노드 자신이 시간을 재고 스스로 끝나는 것. 밖에서 기다려주지 않는다.

문법은 여섯 줄이 전부다

g = StateGraph(ReviewState)          # ① 굴릴 state
g.add_node("security", 함수)          # ② 이름 ↔ 함수
g.add_edge(START, "security")        # ③ 시작점
g.add_edge("security", "aggregate")  # ④ 잇기
g.add_edge("aggregate", END)         # ⑤ 끝
graph = g.compile(checkpointer=...)  # ⑥ 설계도 확정

②에서 준 이름이 ③④에서 다시 쓰인다. 오타를 내면 그 노드는 영원히 안 돌거나 컴파일에서 잡힌다.

조건부 엣지는 언제 쓰나

add_conditional_edges(출발, 함수) 는 갈 곳이 실행 시점에 정해질 때만 쓴다.

갈 곳이쓸 것
upbit 프로젝트이상치 유형에 따라 다름 — 뉴스를 볼 때도, 안 볼 때도add_conditional_edges
PR 리뷰 (여기)항상 넷 다add_edge 넷

조건이 없는데 조건부 엣지를 쓰면 "항상 같은 값을 반환하는 함수" 를 하나 만들게 된다. 읽는 사람은 "여기 분기가 있구나" 하고 조건을 찾다가 없는 걸 확인하게 된다.

조립과 실행은 다른 시간대다

__init__()  →  add_node · add_edge · compile()     # 딱 한 번. 설계도
run()       →  graph.invoke(state, config)         # 리뷰마다. superstep 은 여기서 생긴다

설계도에는 superstep 이 없다. 그림에 층이 보이는 건 우리가 눈으로 세는 것이고, LangGraph 는 invoke() 할 때 비로소 층을 긋는다.

그래서 compile() 을 run() 안에서 부르면 안 된다 — 리뷰 1000건에 똑같은 설계도를 1000번 만드는 것이다. 리뷰를 구분하는 건 그래프가 아니라 thread_id 하나다.

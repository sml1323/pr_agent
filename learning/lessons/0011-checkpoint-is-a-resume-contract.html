체크포인트는 저장이 아니라
재개 계약이다

"어디까지 했나"를 다른 프로세스가 읽을 수 있어야 계약이 성립한다.

M5 완료 판정 ② "워커를 kill -9 로 죽이고 다시 띄우면 이미 끝난 에이전트를 다시 안 부른다."

이건 INV-2(같은 배달 두 번 = 한 번)가 오케스트레이션 층에서 지켜지는 자리다. 다시 부르면 LLM 호출이 두 번 나가고, 같은 findings 가 두 벌 생긴다.

장면부터 — 프로세스 두 개를 띄워봤다

프로세스 A 에서 리뷰를 끝까지 돌리고, 프로세스 B 에서 같은 열쇠로 상태를 읽었다. 체크포인터는 InMemorySaver: 

$ python ck.py run    # 프로세스 A
프로세스 A: done · findings 4

$ python ck.py read   # 프로세스 B — 같은 thread_id
프로세스 B: not_started · findings 0
저장은 됐다. 다만 그 프로세스 안에서만.
프로세스가 죽으면 저장한 것도 같이 죽는다.

InMemorySaver 는 파이썬 defaultdict 하나다. 라이브러리가 대놓고 적어뒀다:

1차 출처 "Only use InMemorySaver for debugging or testing purposes. For production use cases we recommend installing langgraph-checkpoint-postgres and using PostgresSaver."
— langgraph.checkpoint.memory.InMemorySaver 독스트링 (설치된 패키지)

⚠️ 여기서 M5-3 의 결정 하나가 목숨을 구했다

프로세스 B 가 not_started 라고 말했다. 만약 get_state() 가 is_done 불리언이었다면 어땠을까 —

프로세스 B 가 본 것is_done 이었다면status 3값이라서
snapshot.next 가 비어 있다True — "이미 끝났다" 💥not_started ✅
워커가 하는 일스킵. 리뷰가 통째로 유실처음부터 돌린다

시작 전과 완료 후는 둘 다 next 가 비어 있다. 구분자는 created_at 이었고, 그걸 M5-3 에서 status 세 값으로 갈라뒀다. Lesson 06 의 "빈 것의 뜻이 여럿이다"가 여기서 또 나온다.

고를 것 ① — 어디에 저장하나

어디kill -9 를 넘나설치
InMemorySaver프로세스 메모리❌ 원리적으로 불가이미 있음
SqliteSaver파일 하나⭕langgraph-checkpoint-sqlite
PostgresSaver이미 떠 있는 DB⭕langgraph-checkpoint-postgres

지금 실제 상태 뒤의 둘은 설치돼 있지 않다. 확인했다 — No module named 'langgraph.checkpoint.sqlite'. 즉 이 결정은 uv add 를 부른다. 공짜인 선택지는 완료 판정을 못 넘는 것 하나뿐이다.

Postgres 를 고르면 — "엔진은 DB 를 모른다"가 깨지나?

M5-1 에서 "엔진은 DB 를 모른다"고 못 박았다. 그런데 체크포인터가 Postgres 면? 

def __init__(self, checkpointer: BaseCheckpointSaver | None = None):
    self._checkpointer = checkpointer      # 받기만 한다

안 깨진다. 엔진이 아는 건 BaseCheckpointSaver 라는 모양뿐이고, 그게 메모리인지 파일인지 Postgres 인지는 부르는 쪽이 정한다. M5-1 에서 주입 구조로 만들어둔 것이 여기서 이자를 낸다 — 그때 "무엇을 쓸지는 M5-6 의 결정이고 이 클래스는 몰라도 된다"고 적어둔 그 자리다.

⚠️ 다만 004 의 그 DB 를 쓸 것인가는 별개 질문이다. 같은 Postgres 인스턴스에 LangGraph 가 자기 테이블을 만든다 (checkpoints, checkpoint_writes …). 우리 reviews·findings 와 한 DB 에 섞이는 것이 좋은지 나쁜지 — 그게 판단이다.

고를 것 ② — 열쇠는 이미 정해져 있다

config = {"configurable": {"thread_id": review_key}}

M5-1 에서 review_key 를 PR 정보(repo·pr_id·head_sha)로 계산하기로 했다. 저장이 아니라 계산이라 죽었다 살아난 워커가 같은 열쇠를 다시 만들어낸다.

열쇠를 run() 의 반환값으로 뒀다면
kill -9 된 순간 그 값은 존재한 적이 없다.

고를 것 ③ — 무엇을 저장하나 (진짜 판단)

우리 findings 채널에는 Finding(Pydantic 객체)이 들어 있다. 돌릴 때마다 경고가 뜬다: 

WARNING langgraph.checkpoint.serde.jsonplus:
  Deserializing unregistered type backend.agents.schema.Finding from checkpoint.
  This will be blocked in a future version.

이걸 "정리 좀 하라"는 잔소리로 읽으면 절반을 놓친다. 보안 경계다 —

1차 출처 "Msgpack deserialization safety controls. Set LANGGRAPH_STRICT_MSGPACK=true to restrict checkpoint deserialization to the types listed in SAFE_MSGPACK_TYPES. Without this, any Python callable stored in checkpoint data will be imported and executed on load."
— langgraph/checkpoint/serde/_msgpack.py 모듈 독스트링 (설치된 패키지)

체크포인트를 읽는다는 건 거기 적힌 타입을 import 한다는 뜻이다. 그래서 기본 허용 목록(SAFE_MSGPACK_TYPES)에는 datetime·UUID· Decimal·Path 같은 것들만 있고, 우리 클래스는 없다. Lesson 02 의 "이 데이터를 누가 썼나"가 저장소로 옮겨온 것이다 — DB 를 만질 수 있는 사람이 체크포인트를 고치면 어떻게 되나.

그래서 갈림길이 둘

(A) 허용 목록에 Finding 추가(B) dict 로 눕혀서 저장
코드노드는 그대로노드가 .model_dump() 를 부른다
타입 안전꺼낼 때 Finding 그대로꺼내면 dict — 다시 감싸야 한다
필드를 하나 바꾸면저장된 체크포인트를 못 읽는다키가 하나 빌 뿐
저장 포맷이 묶이는 대상우리 파이썬 클래스없음

이미 겪은 긴장이다 004 findings 테이블에서 우리는 이미 (B)를 골랐다 — JSON 한 덩어리로 밀어 넣지 않고 컬럼으로 눕혔다. 같은 질문이 다른 저장소에서 다시 나온 것이고, 여기서 다르게 고를 이유가 있는지가 판단이다. 힌트: 체크포인트는 004 와 달리 영구 보관물이 아니다.

재개는 어떻게 INV-2 를 지키나

Lesson 07 에서 실측한 것 — 한 superstep 이 실패하면 채널에는 아무것도 커밋되지 않지만, 이미 끝난 노드의 출력은 따로 남는다. 

checkpoint         ← 층이 통째로 닫혀야 갱신된다
pending_writes     ← 노드 하나가 끝날 때마다 즉시 적힌다  (put_writes)

1차 출처 "Store intermediate writes linked to a checkpoint." — BaseCheckpointSaver.put_writes 독스트링
"These per-task writes ensure successful nodes' outputs are durable and don't need re-running on resume." — LangGraph — Checkpointers

resume() 이 invoke(None, ...) 인 이유가 이거다 — "새로 시작하지 말고, pending_writes 에 없는 것만 돌려라."

체크포인터가 없으면 pending_writes 가 존재하지 않는다.
즉 resume() 은 기능이 아니라 저장소의 부수효과다.

⚠️ 그런데 "끝난"의 기준이 타이밍에 달렸다

Lesson 07 에서 같은 코드를 두 번 돌려 결과가 갈렸다. 살아남는 건 "죽은 순간까지 이미 끝나 있던" 노드뿐이고, 그건 스케줄링이 정한다.

그래서 재개가 보장하는 건 "덜 부른다"이지 "정확히 한 번"이 아니다. 넷 중 셋이 끝난 상태로 죽으면 셋을 건너뛰지만, 아슬아슬하게 끝난 하나는 다시 불릴 수 있다. 진짜 "정확히 한 번"은 M6 에서 호출 자체를 멱등하게 만들어야 나온다.

  2. 저장소 없음 에러가 난다

  2. 끝난 걸로 읽고 스킵한다
  3. 판정을 못 내리고 멈춘다

  1. 읽을 때 코드가 실행된다
  2. 저장 용량이 너무 커진다
  3. 읽는 속도가 많이 느리다

재개가 이미 끝난 노드를 건너뛸 수 있는 근거는?

  1. 층마다 체크포인트가 남아서
  2. thread_id 가 진행도를 담아서
  3. 노드별 write 가 따로 남아서

우리 코드에 착지

LangGraphEngine.__init__(checkpointer=None) 의 그 인자다. 지금은 데모에서 InMemorySaver 를 손으로 끼워주고 있고, 기본값이 None 이라 resume() 이 성립하지 않는다.

M5-6 에서 정할 것 셋 — 어디에 저장하나 · 004 의 DB 를 쓰나 · Finding 을 그대로 두나. 셋 다 "지금 편한 것"이 아니라 "완료 판정 ②를 넘는가"로 갈린다.

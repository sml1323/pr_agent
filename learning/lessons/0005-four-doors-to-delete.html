삭제로 가는
문은 네 개다

감사 로그를 "못 지우게" 만들려면, 먼저 지울 수 있는 길을 다 세어야 한다.

여기서 땅이 바뀐다. 01~04는 파이썬·HTTP·LLM API 얘기였다. 05부터는 데이터베이스다. SQL을 몰라도 따라올 수 있게 아래 세 절을 먼저 깔았다. 이미 아는 내용이면 건너뛰어도 된다.

0-a. 우선 agent_events가 뭔가

시스템에서 일어난 모든 일을 한 줄씩 적는 공책이다. PR 하나가 들어오면 이런 일들이 순서대로 일어나고, 각각이 한 줄씩 쌓인다.

tsagentevent_typepr_idcost_usd
10:00:01webhookreceived42—
10:00:01queueenqueued42—
10:00:03securityllm_call420.004
10:00:07gateauto_posted42—

이 표가 있어야 답할 수 있는 질문들이다 — "이 PR 리뷰에 얼마 들었나", "어제 왜 비쌌나", "이 자동 게시된 코멘트, 무슨 근거로 통과됐나". 전부 나중에 따져 묻는 질문이다.

0-b. 그래서 왜 "못 지우게" 하나

위 질문들이 전부 사후 추궁이기 때문이다. 사고가 났을 때 이 공책을 보고 따지는데, 공책을 고칠 수 있으면 사고 낸 사람이 조용히 지울 수 있다.

고칠 수 있는 감사 로그는 감사 로그가 아니다.
그래서 이 프로젝트의 INV-4는 agent_events를 수정·삭제 불가로 못 박는다.

그리고 코드로 막지 않고 DB로 막는다. 코드 규칙("여기서는 지우지 마세요")은 누군가 까먹거나 우회한다. DB가 거부하면 누가 무슨 도구로 접속하든 물리적으로 불가능하다.

0-c. SQL에서 데이터를 없애는 방법 — 셋이 다르다

이 셋의 차이가 이 레슨 전체를 만든다. 겉보기엔 비슷한데 DB 안에서 완전히 다른 일을 한다.

UPDATE agent_events SET cost_usd = 0    줄의 값을 고친다
DELETE FROM agent_events               줄을 하나씩 지운다
TRUNCATE agent_events                  표를 통째로 비운다  ← 별개의 명령

UPDATE와 DELETE는 줄(row) 단위다 — "이 줄을 고쳐라 / 이 줄을 없애라". TRUNCATE는 줄을 하나도 보지 않는다. "표를 비워라" 한 마디로 끝낸다. 이 차이가 뒤에서 함정이 된다.

0-d. 트리거 — DB에 심는 감시자

트리거(trigger)는 "이 표에 무슨 일이 일어나려 하면 이 함수를 먼저 실행해라"라는 규칙이다. DB 안에 심어두면 누가 접속하든 발동한다. 

CREATE TRIGGER 이름
    BEFORE DELETE ON agent_events   ← 지우려 하면, 지우기 전에
    FOR EACH ROW                    ← 줄마다
    EXECUTE FUNCTION 거부함수();     ← 이걸 실행 (예외를 던진다)

거부 함수가 예외를 던지면 그 명령 전체가 취소된다. 이게 INV-4를 DB 레벨에서 강제하는 방법이다.

이 레슨이 주는 것

여기까지가 준비물이다. 이제 진짜 질문 — 트리거를 걸면 끝인가?
INV-4를 DB에 새기려면 지우는 방법이 몇 가지인지부터 세어야 한다. 끝나면 왜 트리거 하나로는 부족한지, 그리고 왜 방어가 두 겹(트리거 + 롤)이어야 하는지를 "그렇게 하라고 적혀 있어서"가 아니라 구조 때문에 설명할 수 있게 된다.

먼저 — 테이블이 실은 하나가 아니다

agent_events는 하이퍼테이블(hypertable)로 만든다. 겉보기엔 보통 테이블인데, 안에서는 시간 구간별로 여러 개의 실제 테이블로 쪼개져 있다. 그 조각 하나를 chunk라 부른다.

"A chunk is a horizontal partition of a hypertable: it is a table that holds rows for a specific time range... you always insert and query against the hypertable name; the system creates and uses chunks behind the scenes."
— Tiger Docs, Understand chunks 

agent_events            ← 내가 쓰는 이름 (논리)
├── _hyper_1_1_chunk    ← 7/01~07 데이터 (실제 테이블)
├── _hyper_1_2_chunk    ← 7/08~14 데이터 (실제 테이블)
└── _hyper_1_3_chunk    ← 7/15~21 데이터 (실제 테이블)

왜 이렇게 하냐 — 서랍장 비유가 맞다. 옷을 한 통에 다 넣으면 뭘 찾든 통째로 뒤져야 한다. "지난주 것"만 서랍 하나에 모아두면 그 서랍만 열면 된다. 시간순 데이터는 질문이 거의 항상 "언제부터 언제까지"라서, 이 구조가 크게 이긴다.

이 구조를 지금 짚는 이유는 성능이 아니다. 내가 트리거를 거는 대상과 실제로 데이터가 들어 있는 테이블이 다르기 때문이다. 여기서 함정이 나온다.

좋은 소식 — 트리거는 chunk까지 따라간다

하이퍼테이블에 트리거를 걸면 chunk에도 자동으로 붙는다. 직접 확인된 사실이다:

"When you create, alter, drop, enable, or disable a trigger on a hypertable... TimescaleDB propagates the change to every chunk."
— Tiger Docs, Automate tasks with triggers

그리고 하나 더 — 하이퍼테이블은 상속(inheritance)이 아니다. 문서가 명시적으로 "Inheritance is not supported for hypertables"라고 못 박는다. 전파는 상속 덕분이 아니라 TimescaleDB가 직접 복사해 붙이는 동작이다. 이 차이가 뒤에서 한 번 더 나온다.

문 ①②: UPDATE 와 DELETE

이 둘은 row 단위(row-level) 동작이다. "이 줄을 바꿔라 / 이 줄을 없애라". 그래서 BEFORE UPDATE ... FOR EACH ROW와 BEFORE DELETE ... FOR EACH ROW 트리거로 잡아서 예외를 던지면 막힌다. 여기까지가 대부분의 사람이 하는 일이고, 여기서 멈추면 뚫린다.

문 ③: TRUNCATE — DELETE 의 묶음이 아니다

TRUNCATE agent_events는 테이블을 통째로 비운다. 직관적으로는 "DELETE를 전부 하는 것"처럼 보이는데, Postgres에서는 완전히 다른 명령이다.

"TRUNCATE will not fire any ON DELETE triggers that might exist for the tables. But it will fire ON TRUNCATE triggers."
— PostgreSQL Docs, TRUNCATE

즉 문 ②를 아무리 잘 막아도 문 ③은 그냥 열려 있다. 별도로 BEFORE TRUNCATE 트리거를 걸어야 한다. 그리고 여기에 제약이 하나 붙는다:

"Triggers on TRUNCATE may only be defined at statement level, not per-row."
— PostgreSQL Docs, CREATE TRIGGER

당연하다. TRUNCATE는 "줄"을 보지 않으니 FOR EACH ROW가 성립하지 않는다. FOR EACH STATEMENT로 써야 한다. 문마다 잠그는 방식이 다르다는 게 요점이다.

DELETE 트리거만 걸어두고 TRUNCATE 를 시도하면?

  1. DELETE 트리거가 대신 발동해서 막힌다
  2. chunk 로 전파되지 않아서 실패한다
  3. 아무 트리거도 안 걸리고 통째로 비워진다
  4. 권한 부족으로 자동 거부된다

문 ④: drop_chunks — 트리거가 원리적으로 못 막는 문

여기가 이 레슨의 핵심이다. TimescaleDB의 표준 데이터 정리 방법은 row를 지우는 게 아니다:

"TimescaleDB data retention works on chunks, not on rows. Deleting data row-by-row, for example, with the PostgreSQL DELETE command, can be slow. But dropping data by the chunk is faster, because it deletes an entire file from disk."
— Tiger Docs, Understand data retention

파일을 지운다. 줄을 지우는 게 아니다. DML(데이터를 조작하는 명령: INSERT/UPDATE/DELETE) 트리거는 "줄에 무슨 일이 일어날 때" 발동한다. 그런데 drop_chunks()는 chunk 테이블 자체를 DROP 하는 DDL(구조를 바꾸는 명령)이다. 줄에는 아무 일도 일어나지 않는다 — 서랍이 사라진다. 

DELETE FROM agent_events   → 줄을 지운다   → 트리거 발동 ✓
TRUNCATE agent_events      → 표를 비운다   → ON DELETE 안 발동 (별도 트리거 필요)
SELECT drop_chunks(...)    → 파일을 지운다 → DML 트리거 발동 자체가 성립 안 함

그래서 방어가 두 겹인 이유가 여기서 나온다.

문 ④는 트리거로 못 막는다. "깜빡했다"가 아니라 트리거가 도달할 수 없는 층이다. 남는 방법은 하나 — 애초에 그 함수를 부를 권한을 주지 않는 것(RBAC).

정리하면: 트리거는 "무엇을 하려 했나"를 막고, 롤은 "그럴 자격이 없다"를 막는다. 두 층이 막는 대상이 다르므로, 하나로는 원리적으로 부족하다.

미확인 — CREATE RULE

프로젝트 문서에 "CREATE RULE로 막으려 하면 실패한다 — RULE은 쿼리 재작성 단계에서 돌고 하이퍼테이블은 재작성 규칙을 지원하지 않는다"고 적혀 있다 [03:00:45]. 1차 출처에서 이 문장을 아직 찾지 못했다. 확인된 건 "하이퍼테이블은 상속을 지원하지 않는다"까지다.

추측을 사실처럼 쓰지 않는다. 어차피 트리거로 갈 거라 실무엔 영향이 없지만, 근거의 등급은 구분해서 기록한다. Lesson 04의 guid 미확인과 같은 취급이다.

트리거와 롤(RBAC)을 둘 다 걸어야 하는 근본 이유는?

  1. 트리거를 깜빡 빼먹을 수 있어서다
  2. 트리거가 닿지 못하는 층이 있어서다
  3. 트리거만 쓰면 쓰기가 느려져서다
  4. 트리거가 chunk 로 전파되지 않아서다

그리고 이게 아까 못 정한 결정으로 이어진다

문 ④를 잠그면 테이블을 줄일 합법적인 수단이 사라진다. agent_events는 영원히 자란다. 그래서 "payload에 무엇을 넣을 것인가"가 단순한 스키마 취향이 아니라 되돌릴 수 없는 용량 결정이 된다. 증거 스니펫 원문을 통째로 넣기로 하면, 그 선택은 INV-4 때문에 영구적이다.

지금 정하지 않는다. 이 결정은 record_event()를 실제로 쓰는 자리에서 한다. 지금 아는 것으로 충분하다 — 왜 그게 되돌릴 수 없는 결정인지를 알게 된 것.

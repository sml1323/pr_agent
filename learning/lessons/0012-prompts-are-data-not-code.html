severity=critical 이라 M8 게이트가 무조건 사람에게 보내고, confidence=1.0 이라 확신도 필터도 못 거른다. 이 프로젝트 제1원칙("틀린 말을 안 하는 것") 정면 위반인데, 테스트로는 잡을 방법이 없다. 아래 절이 왜 없는지를 설명한다.

코드와 프롬프트는 대칭이 아니다

같은 입력 → 같은 출력?회귀를 무엇이 잡나
verify_signature()⭕ 항상테스트 — 통과/실패 두 값
SYSTEM_PROMPT❌ 매번 다르다테스트가 없다 — 뭘 단언하나

assert len(findings) == 5 를 쓰면 프롬프트를 안 고쳐도 언젠가 깨진다. 우리 모델(gpt-5.6-luna)은 output 토큰의 절반 가까이가 reasoning 이다 (M0 실측: 475 중 291). 매번 다르게 생각하고 매번 다르게 답한다.

그래서 프롬프트에 필요한 건 통과/실패 가 아니라 같은 자로 잰 두 숫자다. 그 자를 뭐라고 부르는지는 이미 이름이 있다:

1차 출처 ① "Graders persist as you make changes to your dataset and prompt, making them a great way to quickly assess whether a prompt or model parameter change leads to improvements."
— OpenAI API — Graders

고정되는 건 채점자와 입력 묶음이고,
움직이는 건 프롬프트다. 지금 우리는 거꾸로 하고 있다.

그런데 우리는 자의 재료를 이미 갖고 있다

fixtures/ 에 셋이 있다 — sample.diff(정상) · sample_injected.diff(인젝션) · sample_emotional.diff(사회공학). 정답을 우리가 안다. 인젝션 fixture 에서 회피 시도를 못 잡으면 그건 회귀다. 숫자를 셀 필요도 없다.

없는 건 데이터가 아니라 "이 셋을 매번 같은 방식으로 돌려 비교하는 자리"다. 그게 아래 1차 출처가 eval fixtures 라고 부르는 것이다.

영상의 전제가 또 뒤집혔다

원본 영상은 "프롬프트 레지스트리를 만들어라, 덮어쓰기 금지" [01:49:29] 라고 한다. OpenAI 는 실제로 그 서비스를 만들었다가 접는 중이다:

1차 출처 ② "Prompt creation will be de-emphasized beginning June 3, 2026, and v1/prompts is scheduled to shut down on November 30, 2026."

"Move the prompt content out of the managed prompt object and into your application code. This gives you more control over review, testing, deployment, and versioning."

"Don't scatter prompts inline across the codebase. Create a small prompts/ module, keep each prompt as a named builder function, and add lightweight eval fixtures so prompt changes are reviewed like product logic."
— OpenAI API — Migrate from prompt objects

읽는 법이 두 겹이다:

  • 영상이 노린 것은 살아있다 — 프롬프트를 코드에서 떼어내 별도 모듈로, 리뷰와 테스트를 붙여서. 우리 backend/prompts/ 가 그 문장 그대로다.
  • 다만 서비스로 만들지 않는다 — 만든 쪽이 3개월 뒤 끄는 물건을 우리가 다시 만들 이유가 없다. 저장소는 이미 있다. git 이다.

"덮어쓰기 금지"의 정확한 모양

그럼 불변성은 어디서 오나. 실제로 도는 시스템 하나가 답을 보여준다 — LangSmith 의 프롬프트 허브:

1차 출처 ③ "Commit tags are labels that reference a specific commit in your prompt's version history." · "Each tag references exactly one commit, though you can reassign a tag to point to a different commit." · "By referencing tags rather than commit IDs in your code, you can update which version is being used without modifying the code itself."
— LangSmith — Manage prompts

가리키는 것움직이나같은 모양
commit프롬프트 내용 한 벌❌ 불변git commit · 003_immutable.sql
tagcommit 하나⭕ 옮긴다git branch · latest 심볼릭 링크

"덮어쓰기 금지"는 내용에만 걸린다. 무엇을 쓸지 고르는 포인터는 자유롭게 움직인다. 둘을 한 덩어리로 보면 "그럼 프롬프트를 영영 못 고치나?" 라는 막다른 길로 간다.

그래서 갈림길 — 파일 이름에 번호를 다나

git 이 이미 commit 을 준다. 그럼 security_v1.py 같은 번호가 왜 또 필요한가?

(A) 번호 붙인 불변 파일(B) 파일 하나 + git
모양security/v1.py v2.pysecurity.py
고칠 때새 파일을 만든다그 파일을 고친다
돌던 코드가 자기 버전을안다 (문자열 "v2")모른다 (심어야 안다)
파일 수계속 는다넷 고정
둘을 나란히 돌리기import 두 개못 한다 (브랜치를 갈아야)

판별 기준은 취향이 아니라 우리가 이미 지고 있는 제약이다. M3 의 record_event() 가 agent_events 에 호출 기록을 남기고, 그 표는 INV-4 로 지울 수 없다. 3주 뒤 "이 finding 은 어느 프롬프트가 만든 건가"를 묻게 되는데 —

그 답이 실행 시점에 문자열로 있어야 기록에 남는다.
git SHA 는 파일 안에 안 적혀 있다. 코드는 자기가 어느 커밋인지 모른다.

그리고 우리는 같은 모양을 이미 하나 갖고 있다 — migrations/001_extensions.sql 부터 004_truth.sql 까지. 거기서 번호를 단 이유를 그대로 옮겨올 수 있는지, 아니면 다른 상황인지가 이번 판단이다.

회상 연습

프롬프트를 한 줄 고치고 다시 돌렸더니 findings 가 3개에서 2개가 됐다. 회귀인지 개선인지 판정하려면 무엇이 고정돼 있어야 하나?

  1. 모델 이름과 호출 파라미터
  2. 채점 기준과 입력 데이터셋
  3. 출력 스키마의 필드 목록
  4. 프롬프트 파일의 버전 번호

git 이 이미 커밋으로 버전을 준다. 그런데도 프롬프트 파일 이름에 번호를 다는 이유로 가장 강한 것은?

  1. git 히스토리가 지워질 수 있어서
  2. 돌아가는 코드가 자기 버전을 남겨서
  3. 롤백할 때 되돌리기가 빨라져서
  4. 리뷰어가 변경점을 읽기 편해서

1차 출처 — 이건 꼭 읽을 것

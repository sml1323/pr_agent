kill -9 후 재개

데모에서 워커를 진짜로 죽이고 이어붙이려면 무엇을 타이핑하나.

이 문서가 답한 것 M5 완료 판정 ②("kill -9 로 죽이고 다시 띄우면 이미 끝난 에이전트를 다시 안 부른다")를 실제 프로세스로 증명하려면 무엇이 필요한가.
실행 근거: scratch/recon_kill9_resume.py — 돌리면 아래 숫자가 재현된다.

기본 호출 — 복붙 가능

# 부모 — 워커를 띄우고, 그래프가 시작된 뒤 0.5초에 죽인다
worker = subprocess.Popen([sys.executable, WORKER, "--child"],
                          stdout=subprocess.PIPE, text=True)
worker.stdout.readline()          # "READY" 를 기다린다 ← 함정 ④
time.sleep(0.5)
alive = worker.poll() is None     # 정말 살아 있었나 ← 함정 ②
worker.kill()                     # = SIGKILL
rc = worker.wait()                # 좀비 방지 ← 함정 ③

# 자식 — 그래프를 돌린다
with SqliteSaver.from_conn_string(SQLITE) as saver:
    engine = LangGraphEngine(checkpointer=saver)
    print("READY", flush=True)    # import·조립이 끝난 시점
    engine.run(KEY, diff)

# 다시 부모 — 이어서 돌린다
before = engine.get_state(KEY)
len(before.get("findings", []))   # .get() 이다 ← 함정 ⑤
engine.resume(KEY)

함정

① SIGKILL 은 가로챌 수 없다 — 그래서 이게 진짜 시험이다

signal.signal(signal.SIGKILL, handler)
→ OSError: [Errno 22] Invalid argument

📌 실측. 자식이 "정리하고 죽는" 코드를 돌릴 기회가 없다. 그래서 살아남는 건 죽기 전에 이미 디스크에 착지한 것뿐이고, 그게 pending_writes 가 하는 일이다. SIGTERM(terminate())으로 대신하면 자식이 핸들러로 정리할 수 있어 시험이 헐거워진다.

② 이미 끝난 프로세스를 kill() 하면 조용히 아무 일도 안 난다

p.wait()      # 이미 끝났다
p.kill()      # 예외 없음. 아무 일도 안 일어남

소스 "Skip signalling a process that we know has already died." — send_signal 이 poll() 후 returncode is not None 이면 그냥 return 하고, 그 뒤 os.kill 의 ProcessLookupError 도 pass 로 삼킨다 (subprocess.py:2192-2222, bpo-40550).

⚠️ 그래서 데모가 "0.5초에 죽였다"고 말해도 실제로는 안 죽였을 수 있다. worker.poll() is None 을 kill 직전에 찍어서 근거를 남길 것.

③ wait() 를 안 부르면 좀비가 남는다

소스 "Not reading subprocess exit status creates a zombie process which is only destroyed at the parent python process exit" — Popen.__del__ (subprocess.py:1137). ResourceWarning 을 띄우지만 기본 설정에서는 안 보인다.

④ 부모의 sleep(0.5) 는 "그래프 0.5초 지점"이 아니다 ⚠️ 이게 제일 크다

실측 (3회)
자식 프로세스 전체 시작0.42초
└ 그중 import langgraph + 우리 모듈0.34초
우리 그래프 전체 실행0.81초

📌 시작 오버헤드가 그래프 길이의 절반이다. Popen 직후 sleep(0.5) 하면 그래프는 겨우 0.08초 지점이고, 그때는 체크포인트가 하나도 없어 get_state() 가 not_started 를 돌려준다 — 죽인 게 아니라 시작도 안 한 것인데 결과만 보면 구분이 안 된다.

해법: 자식이 조립을 끝낸 뒤 READY 를 찍고, 부모가 그걸 읽고 나서 시계를 잰다.

⑤ get_state() 가 약속한 키를 항상 주지 않는다

mid-superstep 에 죽으면 snapshot.values 가 통째로 비어 있을 수 있다. 그러면 우리 get_state() 는 **snapshot.values 를 펼치므로 findings 키가 아예 없다 → 호출부의 s["findings"] 가 KeyError. 

kill 아주 이른 시점  → get_state() 키 = ['next_nodes', 'status']              ← 4개가 없다
kill 그래프 진행 중  → 키 = ['diff','failed_agents','findings','next_nodes','review_key','status']

📌 실측. M5-3 이 "반환 키 6개"라고 약속했는데 지켜지지 않는다. 지금은 .get("findings", []) 로 방어하지만, 계약 쪽을 고칠지가 열린 결정이다.

찾아봤는데 없는 것

  • durability="sync" 가 이 조건에서 결과를 바꾸지 않았다 — 0.5초·0.7초 kill 에서 async 와 sync 의 복원 결과가 같았다. ⚠️ 우리 그래프가 superstep 2개짜리로 짧아서일 수 있다. 긴 그래프에서는 재검증할 것.
  • 프로세스 그룹은 안 봤다 — 워커가 자식을 또 낳으면 worker.kill() 이 손자를 안 죽인다(start_new_session=True + os.killpg 가 필요). 지금 워커는 자식을 안 낳으므로 확인하지 않았다.

미검증 잔여

  • Postgres 체크포인터로는 안 돌려봤다 — 지금 Sqlite 를 골랐고 langgraph-checkpoint-postgres 는 설치돼 있지 않다.
  • 여러 워커가 같은 sqlite 를 여는 경우 — 잠금 다툼은 확인하지 않았다. 워커가 한 대라서.

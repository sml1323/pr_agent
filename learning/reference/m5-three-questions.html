Q1 — 커밋된 적 없는 결과가 어떻게 살아남았나

kill 순간 채널(state)에는 아무것도 커밋되지 않았다. 그런데 docs·quality 의 Finding 은 resume 때 재사용됐다. 어디에, 어떤 자격으로 남아 있었나?

우리 코드의 장면

backend/orchestration/langgraph_engine.py — _run_specialist()
    return {"findings": [finding.model_dump()]}  # ← 노드는 "쪽지"를 반환한다

노드는 state 를 편집하지 않는다. 쪽지를 반환하면 그다음은 LangGraph 의 일인데, 저장이 두 단계로 갈라져 있다는 게 핵심이다.

checkpoint (사진)pending_writes (낱장 메모)
언제 기록층(superstep)이 닫힐 때 — 리듀서가 쪽지들을 채널에 합친 뒤 노드가 쪽지를 반환하는 즉시, 노드별로 하나씩
담는 것채널 전체 (findings·failed_agents·…)그 노드의 쪽지 하나
kill 0.5초 시점입력 시점 사진뿐 (findings 0)docs·quality 메모 2장 ✓

그래서 resume 이 하는 일

resume(KEY) = invoke(None) → 체크포인트 로드 (사진: 아직 입력 시점) → 같은 층을 다시 세운다: [security, quality, testing, docs] → 단, pending_writes 에 메모가 있는 노드는 실행을 건너뛰고 메모를 재사용 → security·testing 만 다시 돈다 → 층 닫힘 → 리듀서가 메모 4장 합침

1차 출처: "successful nodes … don't repeat when resumed" — Lesson 07 에서 "entire superstep is transactional" 과 층이 다르다는 걸 실측으로 가른 그 문장. 채널 커밋은 트랜잭션(전부 아니면 전무)이지만, per-task writes 는 노드 단위로 즉시다.

⚠️ 덧붙임: 살아남는 목록은 타이밍이 정한다 — 0.5초에 죽였으니 0.4초(quality)·0.3초(docs)만 메모를 남겼다. 0.35초에 죽였다면 docs 하나뿐이었다. "정확히 한 번"이 아니라 "덜 부른다"인 이유.

스스로 답해보기 — "쪽지는 ___에 ___ 자격으로 남아 있다가, resume 이 ___ 해서 재사용된다"를 네 말로.
힌트 (답하고 나서 열 것) sqlite 의 pending_writes 에 · "이 노드는 이 층에서 이미 끝났다"는 노드 단위 기록으로 · resume 이 같은 층을 다시 세울 때 메모 있는 노드의 실행을 건너뛰어서. 채널 커밋(리듀서)은 층이 닫힐 때 한 번뿐이라는 대비까지 말하면 완전하다.

Q2 — 왜 하필 openai.APITimeoutError 인가

내장 TimeoutError 를 던져도 데모는 똑같이 ✅다. 그런데 왜 SDK 예외를 골랐고, 내장을 던졌다면 뭐가 나중에 잘못되나?

우리 코드의 장면 — except 는 족보로 잡는다

backend/orchestration/langgraph_engine.py — _run_specialist()
    try:
        finding = _call_agent(agent_type)
    except openai.OpenAIError as e:   # 바깥 탓 — APITimeoutError 는 이 족보의 자손
        log.warning(e)                # 한 줄
        return {"failed_agents": [agent_type]}
    except Exception as e:            # 내 탓 의심 — 내장 TimeoutError 는 여기로 떨어진다
        log.exception(e)              # 스택트레이스
        return {"failed_agents": [agent_type]}
족보: openai.APITimeoutError → APIConnectionError → OpenAIError → 첫 번째 절 ✓ 내장 TimeoutError → OSError → Exception → 두 번째 절 ✗ (OpenAIError 의 자손이 아니다)

두 절 다 failed_agents 에 이름을 넣으니 게이트(M8)와 데모 판정은 안 갈린다. 갈리는 건 둘:

잘못 ①로그가 오염된다. 타임아웃은 "예상한 실패"인데 스택트레이스로 기록되면, 3주 뒤 로그에서 진짜 우리 버그(TypeError 오타 같은 것)와 구분이 안 된다 — Lesson 09 가 지키려던 구분이 무너진다.
잘못 ②M6 에서 고칠 곳이 생긴다. 더미 루프는 M6 에서 OpenAI(timeout=…) 한 줄로 통째로 바뀌고, 그때 SDK 가 던지는 건 APITimeoutError 다. 지금부터 같은 걸 던져두면 _run_specialist 는 그날 한 줄도 안 바뀐다. 더미의 일은 가짜 결과가 아니라 진짜와 같은 실패 경로를 만드는 것.

실측: 시나리오 ③ 출력이 WARNING … Request timed out. 한 줄이었다 — 첫 번째 절이 받았다는 증거. request= 를 더미가 직접 만드는 건 진짜 호출에서 SDK 가 채우는 자리(openai/_base_client.py:1083)를 흉내낸 것.

스스로 답해보기 — "당장 같은 이유"와 "나중에 갈리는 것 둘"을 네 말로.
힌트 당장 같음: 어느 절이든 반환 쪽지가 같아서 (failed_agents 에 이름). 나중: ① 예상한 실패가 스택트레이스로 남아 로그에서 버그와 뭉개짐 · ② M6 에서 SDK 로 바뀔 때 except 를 고쳐야 하는 결합이 생김.

Q3 — not_started 가 뭉개는 두 상황

get_state() 가 항상 6개 키를 주는 대신, status="not_started" 가 두 상황을 구분 못 하게 됐다. 뭐와 뭐고, 왜 지금은 안 가르나?

우리 코드의 장면

backend/orchestration/langgraph_engine.py — get_state()
    defaults = {"review_key": review_key, "diff": "",
                "findings": [], "failed_agents": []}
    return {**defaults, **snapshot.values, …}   # 기본값이 나가는 건 스냅샷이 없을 때뿐

recon 실측(scratch/recon_get_state_after_kill.py)이 경계를 정확히 그었다: 키가 빠지는(=기본값이 나가는) regime 은 체크포인트 0개일 때 하나뿐이다. mid-superstep kill 은 4채널이 다 차 있다. 그런데 "체크포인트 0개"가 되는 경로가 둘이다:

상황 A — 정말 시작 전상황 B — 시작했는데 흔적 전에 죽음
무슨 일큐에는 있는데 워커가 아직 run() 을 안 부름 invoke() 진입 후, 첫(입력) 체크포인트 기록 전에 kill
관측values={} · created_at=None → not_started — 완전히 동일

왜 지금은 안 가르나 — 둘 다 근거가 있다

①창이 좁다. 입력 체크포인트는 invoke 들어가자마자 찍힌다 — B 가 되려면 그 밀리초 창을 kill 이 정확히 맞춰야 한다.
②갈라도 행동이 안 달라진다. A 든 B 든 워커가 할 일은 "처음부터 run()" 하나다. review_key 가 저장이 아니라 계산이라(repo·pr·sha) 몇 번을 다시 시작해도 같은 열쇠 — 안전하다.
③구분이 필요해지는 건 "무슨 일이 있었나"를 남길 때 — 그건 상태 조회(get_state)가 아니라 M3 record_event 의 몫이다. "지금 상태"와 "무슨 일이 있었나"를 한 dict 에 안 섞는다는 M5-3 결정 그대로.

같은 무늬 세 번째: is_done boolean → status 3값 (시작 전/완료 뭉개짐) · "빈 findings" → status 가 가름 (Lesson 06) · 이번엔 not_started 안의 두 뜻 — 매번 "빈 것/같아 보이는 것의 뜻이 몇 개인가"를 세고, 행동이 갈릴 때만 값을 쪼갠다.

스스로 답해보기 — 두 상황을 말하고, "왜 지금 안 가르나"를 근거 둘로.
힌트 A 정말 시작 전 / B invoke 직후 첫 체크포인트 전 사망. 안 가르는 근거: 창이 밀리초로 좁다 + 어느 쪽이든 다음 행동이 "처음부터 run()"으로 같다 (review_key 가 계산값이라 재시작이 안전). 필요해지면 M3 의 일.
